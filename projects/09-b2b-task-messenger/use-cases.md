двух каналов над одной сущностью задачи и поведение при разрывах связи.

## UC-01 — Постановка задачи клиентом

**Уровень:** цель пользователя · **Основной актор:** Клиент

**Предусловия:** клиент известен системе и связан с записью в CRM.

**Триггер:** клиент обращается через мессенджер или личный кабинет.

**Гарантия минимума:** обращение не теряется ни при каком состоянии
внешних систем.
**Гарантия успеха:** задача создана, чат заведён, участники подключены,
сделка отражена в CRM.

### Основной сценарий

1. Клиент обращается в мессенджер и выбирает тип задачи кнопками.
2. Система разбирает обращение и определяет тип.
3. Система создаёт задачу и связанный с ней чат.
4. Система создаёт сделку в CRM и связывает её с задачей.
5. Система назначает ответственного сотрудника.
6. Сотрудник получает уведомление.
7. Клиент получает подтверждение с номером задачи.

### Альтернативные потоки

**A1. Обращение из личного кабинета** *(шаг 1)* — задача попадает в ту же
воронку; канал происхождения фиксируется.

**A2. Обращение по существующей задаче** *(шаг 3)* — сообщение попадает в
существующий чат, новая задача не создаётся. Иначе одно обсуждение
рассыпается на несколько задач.

**A3. Свободный текст вместо кнопок** — задача создаётся с типом
«требует уточнения», сотрудник уточняет в чате.

### Исключения

**E1. Клиент не идентифицирован** *(шаг 1)* — задача создаётся с пометкой
и направляется на ручную привязку. Отказать в приёме обращения нельзя:
клиент не должен разбираться, почему система его не узнала.

**E2. CRM недоступна** *(шаг 4)* — задача создаётся, событие для CRM
уходит в исходящий журнал. Недоступность внешней системы не может быть
причиной непринятого обращения.

**E3. Нет доступных исполнителей** *(шаг 5)* — задача попадает в общую
очередь, руководитель видит её как нераспределённую.

**E4. Дубль обращения** — повторное нажатие кнопки не создаёт вторую
задачу.

### Постусловия

Успех: задача и чат созданы, исполнитель назначен либо задача в очереди,
событие для CRM гарантированно доставлено или поставлено в очередь.

## UC-02 — Обмен сообщениями между каналами

**Уровень:** цель пользователя · **Основной актор:** Сотрудник
**Заинтересован:** клиент — для него ничего не должно измениться

**Предусловия:** задача существует, чат создан, участники подключены.

**Триггер:** любой участник отправляет сообщение.

**Гарантия минимума:** отправленное сообщение либо доставлено, либо явно
помечено недоставленным. Молчаливой потери не бывает.

### Основной сценарий

1. Участник отправляет сообщение в своём канале.
2. Система сохраняет его с фактическим временем и каналом происхождения.
3. Система публикует событие подписчикам чата.
4. Участники, находящиеся онлайн, получают сообщение немедленно.
5. Участникам офлайн отправляется уведомление.
6. При открытии чата отметка о прочтении обновляется.

### Альтернативные потоки

**A1. Сообщение с вложением** *(шаг 1)* — файл сохраняется в хранилище,
доступ к нему проверяется по правам на задачу.

**A2. Индикатор набора текста** — передаётся участникам без сохранения в
истории.

**A3. Клиент пишет из мессенджера, сотрудник отвечает из веба** — обе
стороны видят единую ленту в правильном порядке.

### Исключения

**E1. Разрыв соединения у получателя** *(шаг 4)* — при переподключении
клиент сообщает метку последнего полученного сообщения, шлюз догружает
разницу. Мобильная сеть рвётся постоянно; без догрузки продукт теряет
доверие за неделю.

**E2. Отправка при отсутствии сети** — сообщение помечается
неотправленным и уходит автоматически после восстановления.

**E3. Внешний мессенджер вернул ошибку доставки** — сообщение остаётся в
истории с пометкой о недоставке клиенту, сотрудник видит это явно.

**E4. Участник потерял доступ к задаче** — соединение разрывается, новые
сообщения не доставляются, история остаётся в системе.

**E5. Сообщения приходят не по порядку** — лента строится по фактическому
времени отправки, а не по времени получения сервером.

### Постусловия

Успех: сообщение сохранено, доставлено онлайн-участникам, поставлено в
очередь для офлайн, состояние прочтения обновлено.

### Нефункциональные требования

- Задержка доставки при штатной нагрузке в 3 000 соединений — в пределах
  согласованного порога.
- Догрузка пропущенного не должна дублировать уже полученные сообщения.
- Отзыв доступа разрывает активное соединение, а не ждёт закрытия вкладки.

## UC-03 — Выполнение задачи сотрудником

**Уровень:** цель пользователя · **Основной актор:** Сотрудник

**Предусловия:** задача назначена, у сотрудника есть доступ.

**Триггер:** сотрудник открывает назначенную задачу.

### Основной сценарий

1. Сотрудник принимает задачу в работу.
2. Система запускает таймер норматива.
3. Сотрудник уточняет детали в чате задачи.
4. Сотрудник выполняет работу и прикладывает результат.
5. Сотрудник переводит задачу на приёмку.
6. Система останавливает таймер и фиксирует, уложились ли в норматив.
7. Клиент получает уведомление о готовности.

### Альтернативные потоки

**A1. Передача задачи другому исполнителю** *(шаг 3)* — таймер
продолжается, смена исполнителя фиксируется в истории. Обнулять таймер при
передаче — способ скрывать просрочки перекидыванием задач.

**A2. Приостановка в ожидании клиента** — таймер приостанавливается,
причина фиксируется. Иначе норматив нарушается по вине ожидания ответа.

**A3. Норматив нарушен** *(шаг 6)* — руководитель уведомляется, задача
продолжает выполняться.

### Исключения

**E1. Сотрудник не берёт задачу в работу** — по истечении срока
руководитель видит её как непринятую.

**E2. Задача возвращена на доработку** — запускается новый цикл со своим
таймером, история прошлого сохраняется. Число циклов — показатель
качества, и его нельзя терять.

**E3. Сотрудник потерял доступ во время работы** — задача помечается
требующей переназначения, история сохраняется.

### Постусловия

Успех: результат приложен, задача на приёмке, факт соблюдения норматива
зафиксирован.

## UC-04 — Приёмка и оценка клиентом

**Уровень:** цель пользователя · **Основной актор:** Клиент

**Предусловия:** задача переведена на приёмку.

**Триггер:** клиент получает уведомление о готовности.

### Основной сценарий

1. Клиент получает уведомление в своём канале.
2. Клиент просматривает результат.
3. Клиент подтверждает приёмку.
4. Система закрывает задачу.
5. Система запрашивает оценку.
6. Клиент ставит оценку и при желании оставляет комментарий.
7. Оценка передаётся в CRM.

### Альтернативные потоки

**A1. Возврат на доработку** *(шаг 3)* — задача возвращается в работу как
новый цикл; клиент указывает, что не так.

**A2. Клиент не отвечает** — по истечении срока задача закрывается
автоматически с пометкой; оценка не запрашивается повторно.

**A3. Оценка без комментария** — принимается; комментарий необязателен.

### Исключения

**E1. Низкая оценка** *(шаг 6)* — руководитель получает уведомление со
ссылкой на задачу. Низкая оценка без реакции обесценивает сам механизм
оценивания.

**E2. Клиент оценивает повторно** — учитывается последняя оценка, история
изменений сохраняется.

**E3. Передача оценки в CRM не удалась** — оценка сохранена в системе,
событие уходит в очередь доставки.

### Постусловия

Успех: задача закрыта, оценка сохранена и передана в CRM, при низкой
оценке руководитель уведомлён.

## UC-05 — Синхронизация с CRM

**Уровень:** подфункция · **Основной актор:** Система

**Предусловия:** интеграция настроена, карта полей согласована.

**Триггер:** изменение задачи либо встречное изменение в CRM.

**Гарантия минимума:** ни одно изменение не теряется; расхождение
разрешается по явному правилу, а не случайно.

### Основной сценарий

1. Изменение задачи и событие для CRM записываются в одной транзакции.
2. Служба синхронизации читает неотправленные события.
3. Поля сопоставляются с моделью CRM.
4. Сделка обновляется.
5. Событие помечается доставленным.

### Альтернативные потоки

**A1. Встречное изменение из CRM** *(шаг 5)* — версии сравниваются,
применяется согласованное правило приоритета, изменение отражается в
задаче.

**A2. Массовая выгрузка** — при первичной настройке синхронизация идёт
пакетами, а не по событию на запись.

### Исключения

**E1. CRM недоступна** *(шаг 4)* — событие возвращается в очередь с
нарастающей задержкой. Пользователь ничего не замечает: для него задача
уже обновлена.

**E2. Сбой между сохранением и публикацией** — благодаря общей транзакции
событие не теряется и публикуется после восстановления.

**E3. Повторная доставка** *(шаг 4)* — обработка идемпотентна по
идентификатору события; сделка не обновляется дважды.

**E4. Конфликт версий** — фиксируется отдельно и попадает в отчёт. Рост
числа конфликтов означает расхождение процессов в двух системах, а не
техническую проблему, — и это должно быть видно.

**E5. Событие не доставлено после исчерпания попыток** — задача
помечается рассинхронизированной, руководитель видит предупреждение.

### Постусловия

Успех: состояние задачи и сделки совпадает, событие помечено
доставленным. Неуспех: событие в очереди, расхождение видно явно.

## UC-06 — Отзыв доступа сотрудника

**Уровень:** цель пользователя · **Основной актор:** Администратор

**Предусловия:** сотрудник имеет активный доступ.

**Триггер:** увольнение, перевод или инцидент безопасности.

### Основной сценарий

1. Администратор отзывает доступ сотрудника.
2. Система разрывает его активные постоянные соединения.
3. Система прекращает доставку новых сообщений.
4. Активные задачи сотрудника помечаются требующими переназначения.
5. Руководитель получает уведомление о задачах на переназначение.
6. Факт отзыва фиксируется в журнале.

### Альтернативные потоки

**A1. Временная приостановка** — доступ приостанавливается без
переназначения задач, история сохраняется.

**A2. Массовый отзыв** — при переводе подразделения задачи
переназначаются пакетно.

### Исключения

**E1. У сотрудника открыт мессенджер в момент отзыва** *(шаг 2)* —
соединение разрывается немедленно. Ждать закрытия вкладки нельзя: это
означало бы, что уволенный сотрудник продолжает читать переписку с
клиентами.

**E2. Незавершённые задачи без замены** — попадают в общую очередь,
руководитель видит их как нераспределённые.

**E3. Попытка входа после отзыва** — отклоняется, попытка фиксируется в
журнале.

### Постусловия

Успех: доступ закрыт, соединения разорваны, задачи помечены для
переназначения, факт зафиксирован в журнале. История сообщений сотрудника
остаётся в системе — она принадлежит компании, а не ему.
