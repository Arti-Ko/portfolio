# User Stories — B2B веб-мессенджер клиентских задач

4 эпика, 16 историй. Приоритизация по MoSCoW, оценка в story points,
критерии приёмки в Gherkin.

## Карта эпиков

| Эпик | Название | Историй | SP | Ценность |
|---|---|---|---|---|
| EP-01 | Чаты и обмен сообщениями | 5 | 42 | Ядро продукта: планку задал Telegram |
| EP-02 | Задачи и нормативы | 4 | 29 | То, ради чего строится веб-интерфейс |
| EP-03 | Интеграция с CRM | 3 | 26 | Убирает двойной ввод и расхождение данных |
| EP-04 | Роли, доступ и безопасность | 4 | 24 | Требование 152-ФЗ и условие корпоративного внедрения |

**Итого: 121 SP.**

### Порядок поставки

Сначала — чат и задача в двух каналах, без CRM. Это проверяет главную
гипотезу: примут ли сотрудники веб-интерфейс, продолжив при этом
обслуживать клиентов, которые остались в Telegram. Если сотрудники
продолжат работать в боте, интеграция с CRM не спасёт продукт.

# EP-01. Чаты и обмен сообщениями

## US-01.1 — Единая лента для двух каналов

**Как** сотрудник, **я хочу** видеть в веб-интерфейсе всю переписку с
клиентом, **чтобы** не переключаться между мессенджером и браузером.

`Must` · `13 SP` · зависимостей нет

```gherkin
Функция: Единая лента сообщений

  Сценарий: Сообщение клиента из мессенджера
    Дано клиент пишет в Telegram-бот
    Когда сообщение доставлено
    Тогда оно появляется в чате задачи в веб-интерфейсе

  Сценарий: Ответ сотрудника из веба
    Когда сотрудник отправляет сообщение в веб-интерфейсе
    Тогда клиент получает его в Telegram

  Сценарий: Порядок сообщений сохраняется
    Дано сообщения приходят из обоих каналов
    Когда лента отображается
    Тогда порядок соответствует фактическому времени отправки

  Сценарий: Виден канал происхождения
    Когда сотрудник открывает историю
    Тогда для каждого сообщения понятно, из какого канала оно пришло
```

## US-01.2 — Доставка в реальном времени

**Как** сотрудник, **я хочу** видеть сообщения мгновенно, **чтобы**
интерфейс не проигрывал Telegram.

`Must` · `13 SP` · после US-01.1

```gherkin
Функция: Real-time доставка

  Сценарий: Мгновенное появление
    Дано у сотрудника открыт чат
    Когда приходит новое сообщение
    Тогда оно появляется без перезагрузки страницы

  Сценарий: Индикатор набора текста
    Когда собеседник набирает сообщение
    Тогда в чате отображается индикатор

  Сценарий: Отметка о прочтении
    Когда участник открывает чат
    Тогда отправитель видит, что сообщения прочитаны

  Сценарий: Три тысячи одновременных сессий
    Дано подключено 3 000 пользователей
    Когда отправляется сообщение
    Тогда оно доставляется участникам чата в пределах установленной задержки
```

## US-01.3 — Восстановление после разрыва связи

**Как** сотрудник, **я хочу** не терять сообщения при потере сети,
**чтобы** доверять интерфейсу.

`Must` · `8 SP` · после US-01.2

```gherkin
Функция: Переподключение

  Сценарий: Догрузка пропущенного
    Дано соединение прерывалось на несколько минут
    Когда оно восстанавливается
    Тогда клиент получает все сообщения за период отключения
    И порядок и содержание не нарушены

  Сценарий: Индикация состояния соединения
    Дано соединение потеряно
    Когда пользователь смотрит на интерфейс
    Тогда он видит явный признак отсутствия связи

  Сценарий: Отправка при отсутствии сети
    Когда пользователь отправляет сообщение без связи
    Тогда оно помечается неотправленным
    И уходит автоматически при восстановлении
```

## US-01.4 — Вложения

**Как** клиент, **я хочу** прикладывать фото и документы, **чтобы**
объяснить задачу быстрее, чем текстом.

`Must` · `5 SP` · после US-01.1

```gherkin
Функция: Вложения

  Сценарий: Файл из мессенджера
    Когда клиент отправляет фото в Telegram
    Тогда оно доступно в чате веб-интерфейса

  Сценарий: Ограничение размера
    Когда пользователь прикладывает файл сверх лимита
    Тогда загрузка отклоняется с указанием ограничения

  Сценарий: Доступ к вложению по правам
    Когда пользователь без доступа к задаче открывает ссылку на файл
    Тогда доступ отклоняется
```

## US-01.5 — Поиск по переписке

**Как** сотрудник, **я хочу** находить прошлые обсуждения, **чтобы** не
переспрашивать клиента о том, что уже обсуждалось.

`Should` · `3 SP` · после US-01.1

```gherkin
Функция: Поиск

  Сценарий: Поиск по своим чатам
    Когда сотрудник ищет по фразе
    Тогда показаны сообщения из доступных ему чатов
    И переход открывает нужное место в ленте
```

# EP-02. Задачи и нормативы

## US-02.1 — Автоматическое создание задачи и чата

**Как** клиент, **я хочу** ставить задачу так же просто, как раньше,
**чтобы** новый продукт не усложнил мне жизнь.

`Must` · `8 SP` · зависимостей нет

```gherkin
Функция: Создание задачи

  Сценарий: Постановка из мессенджера
    Когда клиент ставит задачу кнопками в боте
    Тогда создаётся задача и чат по ней
    И участники подключаются автоматически

  Сценарий: Задача без ручного создания чата
    Когда задача создана
    Тогда отдельного действия для создания чата не требуется

  Сценарий: Повторное обращение по существующей задаче
    Дано у клиента есть открытая задача
    Когда он пишет в боте
    Тогда сообщение попадает в существующий чат, а не создаёт новую задачу
```

## US-02.2 — Назначение и статусы

**Как** руководитель, **я хочу** видеть, кто чем занят, **чтобы**
распределять нагрузку.

`Must` · `8 SP` · после US-02.1

```gherkin
Функция: Жизненный цикл задачи

  Сценарий: Назначение исполнителя
    Когда задача назначается сотруднику
    Тогда он получает уведомление
    И задача появляется в его списке

  Сценарий: Смена статуса фиксируется
    Когда статус задачи меняется
    Тогда в истории сохраняются прежний и новый статус, автор и время

  Сценарий: Возврат на доработку
    Когда клиент не принимает результат
    Тогда задача возвращается в работу как новый цикл
    И предыдущая история сохраняется
```

## US-02.3 — Нормативы времени

**Как** руководитель, **я хочу** знать о нарушении нормативов, **чтобы**
вмешиваться до жалобы клиента.

`Must` · `8 SP` · после US-02.2

```gherkin
Функция: Нормативы

  Сценарий: Таймер стартует со взятия в работу
    Когда сотрудник принимает задачу
    Тогда запускается таймер норматива
    И время до назначения в него не входит

  Сценарий: Эскалация при нарушении
    Дано норматив по задаче превышен
    Когда это фиксируется
    Тогда руководитель получает уведомление
    И задача продолжает выполняться

  Сценарий: Отдельный таймер на каждый цикл доработки
    Дано задача возвращена на доработку
    Когда сотрудник берёт её снова
    Тогда запускается новый таймер
    И история прошлых циклов сохраняется
```

## US-02.4 — Оценка работы клиентом

**Как** клиент, **я хочу** оценить выполнение, **чтобы** повлиять на
качество сервиса.

`Must` · `5 SP` · после US-02.2

```gherkin
Функция: Оценка

  Сценарий: Оценка после закрытия
    Когда задача закрывается
    Тогда клиент получает запрос оценки в своём канале

  Сценарий: Низкая оценка привлекает внимание
    Дано клиент поставил низкую оценку
    Когда она сохраняется
    Тогда руководитель получает уведомление с ссылкой на задачу

  Сценарий: Оценка попадает в CRM
    Когда оценка сохранена
    Тогда она передаётся в карточку сделки
```

# EP-03. Интеграция с CRM

## US-03.1 — Создание и обновление сделки

**Как** руководитель, **я хочу** чтобы задачи автоматически отражались в
CRM, **чтобы** не вести учёт дважды.

`Must` · `13 SP` · после US-02.1

```gherkin
Функция: Синхронизация в CRM

  Сценарий: Сделка создаётся вместе с задачей
    Когда задача создана
    Тогда в CRM появляется соответствующая сделка
    И обе системы связаны общим идентификатором

  Сценарий: Изменение статуса доходит до CRM
    Когда статус задачи меняется
    Тогда сделка обновляется

  Сценарий: CRM недоступна
    Дано CRM не отвечает
    Когда задача изменяется
    Тогда работа сотрудника не прерывается
    И изменение доставляется после восстановления
```

## US-03.2 — Гарантия доставки изменений

**Как** система, **я хочу** не терять изменения при сбоях, **чтобы**
данные в двух системах не расходились.

`Must` · `8 SP` · после US-03.1

```gherkin
Функция: Гарантия доставки

  Сценарий: Изменение и событие пишутся вместе
    Когда задача изменяется
    Тогда изменение и событие для CRM сохраняются в одной транзакции

  Сценарий: Сбой между сохранением и отправкой
    Дано сбой произошёл после сохранения, но до публикации
    Когда система восстанавливается
    Тогда событие публикуется и данные согласуются

  Сценарий: Повторная доставка не создаёт дублей
    Когда событие доставлено дважды
    Тогда сделка обновляется один раз
```

## US-03.3 — Встречные изменения из CRM

**Как** руководитель, **я хочу** чтобы правки в CRM отражались в
мессенджере, **чтобы** сотрудники видели актуальные данные.

`Should` · `5 SP` · после US-03.2

```gherkin
Функция: Входящая синхронизация

  Сценарий: Изменение сделки в CRM
    Когда данные сделки меняются в CRM
    Тогда соответствующая задача обновляется

  Сценарий: Конфликт версий
    Дано поле изменено в обеих системах
    Когда обнаруживается расхождение
    Тогда применяется согласованное правило приоритета
    И факт конфликта фиксируется

  Сценарий: Рост числа конфликтов виден
    Когда руководитель открывает отчёт синхронизации
    Тогда он видит количество конфликтов за период
```

# EP-04. Роли, доступ и безопасность

## US-04.1 — Ролевая модель

**Как** администратор, **я хочу** разграничить доступ, **чтобы** клиент
видел только свои задачи, а сотрудник — только назначенные ему.

`Must` · `8 SP` · зависимостей нет

```gherkin
Функция: Разграничение доступа

  Сценарий: Клиент видит только свои задачи
    Когда клиент открывает личный кабинет
    Тогда он видит только собственные задачи и чаты

  Сценарий: Сотрудник видит назначенное
    Когда сотрудник открывает список
    Тогда он видит задачи, назначенные на него

  Сценарий: Руководитель видит подразделение
    Когда руководитель открывает список
    Тогда он видит задачи своих сотрудников
```

## US-04.2 — Личный кабинет клиента

**Как** клиент, **я хочу** видеть историю своих задач в вебе, **чтобы**
не листать переписку в мессенджере.

`Should` · `5 SP` · после US-04.1

```gherkin
Функция: Кабинет клиента

  Сценарий: История задач
    Когда клиент входит в кабинет
    Тогда он видит свои задачи со статусами, оценками и историей

  Сценарий: Постановка задачи из кабинета
    Когда клиент создаёт задачу в вебе
    Тогда она попадает в ту же воронку, что и задачи из мессенджера
```

## US-04.3 — Защита персональных данных

**Как** оператор данных, **я хочу** выполнить требования по обработке
персональных данных, **чтобы** продукт можно было внедрять в компании.

`Must` · `8 SP` · после US-04.1

```gherkin
Функция: Обработка персональных данных

  Сценарий: Шифрование контактных данных
    Когда сохраняются ФИО и телефон клиента
    Тогда они хранятся в зашифрованном виде

  Сценарий: Журнал доступа
    Когда сотрудник открывает карточку клиента
    Тогда факт доступа фиксируется в журнале

  Сценарий: Данные не попадают в логи
    Когда система пишет технические логи
    Тогда персональные данные в них отсутствуют
```

## US-04.4 — Отзыв доступа

**Как** администратор, **я хочу** мгновенно закрывать доступ уволенному
сотруднику, **чтобы** он не читал переписку после ухода.

`Must` · `3 SP` · после US-04.1

```gherkin
Функция: Отзыв доступа

  Сценарий: Разрыв активного соединения
    Дано у сотрудника открыт мессенджер
    Когда администратор отзывает доступ
    Тогда постоянное соединение разрывается
    И новые сообщения ему не доставляются

  Сценарий: Переназначение задач
    Когда доступ отозван
    Тогда его активные задачи помечаются требующими переназначения
```

## Definition of Ready

История берётся в спринт, если: определено поведение в обоих каналах —
веб и мессенджер; описано, что происходит при разрыве соединения;
указано, как изменение отражается в CRM; для историй с персональными
данными — определён режим доступа и журналирования.

## Definition of Done

Сценарии Gherkin покрыты автотестами; поведение проверено на нагрузке в
3 000 соединений; проверена доставка после разрыва связи; проверено, что
персональные данные не попадают в логи; поведение при недоступной CRM
проверено намеренным сбоем.
