# Тестовая матрица верификации обезличивания

Матрица определяет, что именно проверяется на приёмочном наборе и какое
поведение считается правильным. Она же служит контрактом между аналитиком,
разработкой и оператором ПДн: спор о том, «ошибка это или нет», решается
ссылкой на строку матрицы, а не мнением.

## Принцип оценки

Ошибки несимметричны, и матрица это фиксирует явно.

| Тип ошибки | Что произошло | Последствие | Вес |
|---|---|---|---|
| Пропуск (FN) | Идентификатор остался в тексте | Утечка ПДн, инцидент с уведомлением регулятора | Блокирующий |
| Ложное срабатывание (FP) | Замаскировано лишнее | Потеря аналитической ценности | Значимый, не блокирующий |
| Неверная стратегия | Идентификатор найден, но обработан не так | Либо утечка, либо порча данных — зависит от случая | Разбирается индивидуально |

Приёмочный критерий: **полнота ≥ 99.9% по каждому типу отдельно.** Среднее по
всем типам не используется — пропуск целого класса идентификаторов не
компенсируется отличными показателями по остальным.

подряд и формально проходит проверку на полноту.

## Матрица: сценарии и форматы

| # | Сценарий | Что проверяет | Ожидаемый результат |
|---|---|---|---|
| S-01 | Обычная выписка, PDF с текстовым слоем | Базовый путь | Все типы обработаны по стратегиям |
| S-02 | Скан без текстового слоя | Отказ вместо частичной обработки | Ошибка «требуется распознавание», документ не сохранён |
| S-03 | HL7 v2 | Структурированные поля и текстовые блоки | Обезличены оба, структура остаётся валидной |
| S-04 | FHIR-ресурс | То же для JSON-структуры | Схема ресурса не нарушена |
| S-05 | Документ с таблицей | ПДн в ячейках | Значения в колонке «Пациент» обработаны как текст |
| S-06 | Пациент упомянут 20 раз в разных формах | Устойчивость псевдонима | Один псевдоним на все вхождения |
| S-07 | Два пациента в одном документе | Разделение субъектов | Разные псевдонимы, не перепутаны между собой |
| S-08 | Врач и пациент — однофамильцы | Контекстное различение | Разные стратегии применены корректно |
| S-09 | Два документа одного пациента | Согласованность сдвига дат | Одинаковый сдвиг, хронология сохранена |
| S-10 | Документ без ПДн | Отсутствие ложных срабатываний | Документ возвращён без изменений, не ошибка |
| S-11 | Опечатка в ФИО («Ивaнов» с латинской «a») | Устойчивость к искажениям | Распознано, замаскировано |
| S-12 | ФИО в диагнозе-эпониме («болезнь Паркинсона») | Отсутствие ложного срабатывания | Не маскируется |
| S-13 | Дата в номере документа («приказ № 12.05.2024/7») | Различение даты и части идентификатора | Обработано корректно, номер не разрушен |
| S-14 | Очень длинный документ (200+ страниц) | Асинхронный путь, отсутствие таймаута | Обработан полностью, результат по callback |
| S-15 | Документ на границе форматов (DOCX с вложенным PDF) | Обработка вложений | Вложение либо обработано, либо явный отказ |

Сценарии S-11, S-12 и S-13 — провокационные. Они существуют, потому что
именно на них ломаются системы, отлично работающие на чистых данных: реальные
медицинские документы содержат опечатки, эпонимы и структуры, где дата не
является датой.

## Матрица: безопасность и аудит

| # | Проверка | Как проверяется | Критерий |
|---|---|---|---|
| SEC-01 | ПДн не попадают в логи приложения | Прогон с максимальным уровнем логирования, поиск по логам | Ни одного вхождения исходных значений |
| SEC-02 | ПДн не попадают в сообщения об ошибках | Намеренный сбой на каждом шаге пайплайна | Сообщения содержат идентификаторы объектов, не содержимое |
| SEC-03 | Временные файлы удаляются | Аварийное завершение процесса в середине обработки | После рестарта временных файлов нет |
| SEC-04 | В хранилище документов нет исходных значений | Прямой запрос к базе после обработки | Только смещения и типы сущностей |
| SEC-05 | Токен-мапа недоступна пайплайну | Попытка чтения из компонента обработки | Отказ на уровне прав СУБД |
| SEC-06 | Неизменяемость аудит-лога | Попытка изменить запись в середине цепочки | Проверка целостности выявляет нарушение |
| SEC-07 | Аудит пишется до возврата результата | Имитация отказа записи в лог | Документ не возвращён, запрос завершён ошибкой |
| SEC-08 | Раскрытие невозможно в обход согласования | Прямой вызов сервиса деанонимизации | Отказ, инцидент в SIEM |
| SEC-09 | Заявитель не может быть согласующим | Попытка самосогласования | Отклонено системой |
| SEC-10 | Срок доступа к раскрытым данным истекает | Обращение после истечения TTL | Доступ закрыт |

## Регламент прогона

**Когда запускается:** при любом изменении модели, правил, словарей или
порогов; перед выпуском версии; ежемесячно планово.

**Где запускается:** в изолированном окружении на эталонном наборе. Боевые
документы в приёмочном наборе не используются — набор собран из
синтетических и обезличенных с ручной перепроверкой примеров.

**Как принимается решение:**

1. Полнота по каждому типу сравнивается с порогом из матрицы — любое
   недостижение блокирует выпуск.
2. Результат сравнивается с предыдущим прогоном — регрессия по любому типу
   разбирается отдельно, даже если абсолютное значение выше порога.
3. Рост числа ложных срабатываний фиксируется и оценивается на влияние
   аналитической ценности, но выпуск не блокирует.
4. Отчёт прикладывается к релизу и хранится вместе с аудитом.

**Эталонный набор фиксирован.** Изменение набора между прогонами делает
результаты несопоставимыми. Если в эталонной разметке найдена ошибка, набор
исправляется, а все предыдущие метрики пересчитываются — история, посчитанная
по неверному эталону, удаляется, а не остаётся «для истории».
