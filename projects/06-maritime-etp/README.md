# ЭТП для морских грузоперевозок

`LOGISTICS / MARITIME` · системный анализ · BPMN, ролевая модель,
электронная подпись, интеграция AIS

Электронная торговая площадка для морских грузоперевозок в арктической
акватории: двухэтапные торги, отслеживание судов по AIS, юридически
значимый документооборот без бумаги.

## Задача

В морской логистике участвуют четыре стороны с несовпадающими интересами:
грузовладельцы, судовладельцы, администрации портов и владельцы
терминалов. Взаимодействие идёт частично по электронной почте, частично
бумагой, единой площадки нет. Сделка собирается звонками, коносамент
подписывается и возит с собой курьер, положение груза узнают у капитана.

Заказчик строит площадку, замыкающую весь цикл — от поиска судна до
закрытия сделки. Цель, вокруг которой собран весь проект: **полный отказ
от бумаги**. Это не про удобство, а про сроки: в арктической навигации
окно ограничено, и неделя на пересылку оригиналов документов может стоить
рейса.

## Специфика домена, определившая архитектуру

**Судно — не грузовик.** Оно не может выехать в любой момент: навигация
ограничена ледовой обстановкой, у порта есть слоты, у судна — ледовый
класс, определяющий, куда оно вообще допущено. Поэтому торги двухэтапные:
сначала допуск по формальным критериям, потом цена. Дешёвое предложение
от судна без нужного ледового класса — не предложение.

**Документы юридически значимы.** Коносамент — не накладная, это
товарораспорядительный документ: тот, у кого он на руках, распоряжается
грузом. Электронная форма требует квалифицированной подписи, иначе
площадка бесполезна — стороны всё равно будут возить бумагу.

**Положение судна известно объективно.** Система AIS передаёт координаты
в реальном времени. Это редкий случай, когда статус исполнения не нужно
запрашивать у контрагента — его можно наблюдать.

## Что сделано как системным аналитиком

- **BPMN-модели морских бизнес-процессов** — от запроса грузовладельца до
  закрытия сделки, включая двухэтапную модель торгов
- **Декомпозиция поставки на три этапа** — минимальный контур → MVP →
  полный продукт, с обоснованием, что и почему попадает в каждый
- **Ролевая модель** для четырёх типов участников с матрицей прав
- **User stories** по всем ролям
- **Оценка технического задания** и финальная оценка разработки
- **План развития продукта** после запуска
