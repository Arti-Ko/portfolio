# Use Cases — Сервис AI-озвучки

Шесть вариантов использования в нотации Коберна. Особое внимание — ролям
продюсера и технического редактора: их зоны ответственности не пересекаются,
и это разделение зафиксировано в каждом сценарии.

## Акторы и зоны ответственности

| Актор | Отвечает за | Не принимает решений о |
|---|---|---|
| Продюсер | Что дублируем, на какие языки, каким голосом; приёмка и публикация | Содержании правок внутри сегмента |
| Технический редактор | Качество текста, произношения и тайминга; глоссарий проекта | Публикации и выборе языков |
| Асессор | Субъективную оценку естественности | Чем-либо ещё — видит только аудио, без метрик |
| Оркестратор (система) | Порядок шагов, повторы, состояние выпуска | Порогами приёмки — они задаются конфигурацией |

## UC-01 — Запуск автоматического дубляжа

**Уровень:** цель пользователя · **Основной актор:** Продюсер
**Заинтересованы:** заказчик локализации (сроки и бюджет), редактор (объём ручной работы)

**Предусловия**
1. Видео доступно на хостинге, у системы есть права на скачивание.
2. Для целевого языка настроен голосовой профиль.
3. Проект содержит глоссарий (возможно, пустой).

**Триггер:** продюсер выбирает видео и целевые языки, нажимает «Запустить дубляж».

**Гарантия минимума:** промежуточные артефакты сохраняются; при сбое на любом
шаге выпуск возобновляется с этого шага, а не с начала.
**Гарантия успеха:** дорожка сведена, автоконтроль пройден, выпуск готов к
публикации.

### Основной сценарий

1. Продюсер выбирает видео и отмечает целевые языки.
2. Система создаёт по одному выпуску на каждый язык.
3. Система скачивает исходник через API хостинга.
4. Аудио-процессор извлекает дорожку и нормализует уровень.
5. Адаптер отправляет аудио в STT, получает транскрипт с тайм-кодами.
6. Сегментатор разбивает транскрипт по фразам и паузам.
7. Адаптер переводит сегменты на целевой язык.
8. Модуль фонетики применяет глоссарий проекта.
9. Генератор SSML размечает произношение, паузы и темп.
10. Адаптер отправляет размеченный текст в TTS посегментно.
11. Модуль тайминга выравнивает длительность сегментов под исходные окна.
12. Микшер сводит дорожку, приводит громкость к целевому уровню.
13. Контроль качества считает WER, рассинхрон, отклонение длительности,
    громкость.
14. Вердикт приёмки сравнивает метрики с порогами.
15. Выпуск переходит в статус «готов к публикации»
    (см. [UC-05](#uc-05--публикация-дорожки-на-видеохостинге)).

### Альтернативные потоки

**A1. Выпуск на этот язык уже существует** *(шаг 2)*
Система открывает существующий выпуск вместо создания дубликата. Повторный
запуск возможен только явной командой «Пересобрать».

**A2. В видео нет речи** *(шаг 5)*
Выпуск завершается статусом «нет речи для дубляжа». Перевод и синтез не
запускаются, деньги провайдерам не платятся.

**A3. Часть сегментов не уложилась в тайминг** *(шаг 11)*
Сегменты помечаются флагом переполнения. Пайплайн продолжается: решение
принимает шаг 14 по совокупности метрик, а не отдельный сегмент.

**A4. Пересборка после изменения глоссария** *(шаг 8)*
Пересинтезируются только сегменты, содержащие изменённые термины. Шаги 3–7
переиспользуют сохранённые артефакты.

### Исключения

**E1. Исходник недоступен на хостинге** *(шаг 3)*
Три попытки с нарастающей задержкой. При исчерпании — статус «исходник
недоступен», продюсер получает уведомление. Выпуск не удаляется и может быть
возобновлён.

**E2. STT-провайдер вернул ошибку или таймаут** *(шаг 5)*
Три повтора, затем статус «ошибка распознавания». Скачанный исходник
сохраняется — при возобновлении шаг 3 не повторяется.

**E3. Превышена квота провайдера** *(шаги 5, 7, 10)*
Задача возвращается в очередь с задержкой до конца квотного окна. Если для
языка настроен запасной провайдер — используется он, факт замены фиксируется
в выпуске и отражается в отчёте сравнения.

**E4. TTS не поддерживает элемент разметки** *(шаг 10)*
Неподдерживаемый тег удаляется, синтез выполняется. В выпуске фиксируется
предупреждение — редактор видит, что разметка применена не полностью.

**E5. Сегмент не укладывается даже при максимальном ускорении** *(шаг 11)*
Ускорение ограничивается порогом разборчивости, сегмент помечается как
требующий ручного вмешательства. Система не растягивает речь до неразборчивости
ради формального соблюдения тайминга.

**E6. Автоконтроль отклонил выпуск** *(шаг 14)*
Выпуск переходит в статус «требует правки», создаётся задача редактору —
переход к [UC-03](#uc-03--ручная-правка-отклонённого-выпуска). Это штатный
исход, а не сбой.

### Постусловия

| Исход | Состояние |
|---|---|
| Успех | Дорожка сведена, метрики в допуске, выпуск готов к публикации |
| E6 | Дорожка сведена, метрики зафиксированы, задача у редактора |
| E1–E3 | Выпуск в статусе ошибки, промежуточные артефакты сохранены |

### Нефункциональные требования

- Дубляж часового видео на один язык — не более 40 минут при доступных
  провайдерах.
- Каждый шаг идемпотентен: повторный запуск не создаёт дублей артефактов и
  не тарифицируется повторно.
- Стоимость минуты дубляжа фиксируется по каждому выпуску — без этого нельзя
  проверить достижение цели −75%.

**Частота:** до 50 выпусков в сутки.

## UC-02 — Фонетическая коррекция через глоссарий

**Уровень:** цель пользователя · **Основной актор:** Технический редактор

**Предусловия:** проект существует, редактор имеет права на его глоссарий.

**Триггер:** редактор обнаружил неверное произношение термина либо система
предложила кандидата в глоссарий.

### Основной сценарий

1. Редактор открывает глоссарий проекта.
2. Редактор добавляет термин и указывает язык.
3. Редактор задаёт транскрипцию или помечает термин как непереводимый.
4. Система проверяет корректность транскрипции для выбранного провайдера.
5. Редактор прослушивает пробный синтез термина.
6. Редактор сохраняет запись.
7. Система находит выпуски проекта, содержащие термин.
8. Редактор запускает точечный пересинтез затронутых сегментов.

### Альтернативные потоки

**A1. Термин уже есть в глоссарии** *(шаг 2)* — открывается существующая
запись для правки; дубликаты по паре «термин + язык» не создаются.

**A2. Термин добавляется из списка кандидатов** *(шаг 1)* — система заранее
подставляет термин и показывает выпуски, где он правился вручную.

**A3. Правило без транскрипции** *(шаг 3)* — термин помечается непереводимым:
он сохраняет исходное написание при переводе, но произносится по правилам
целевого языка.

**A4. Редактор отказывается от пересинтеза** *(шаг 8)* — правило применяется
только к будущим выпускам, существующие остаются как есть.

### Исключения

**E1. Транскрипция не принимается провайдером** *(шаг 4)* — система показывает
ошибку валидации и поддерживаемый формат для этого TTS. Запись не сохраняется
в некорректном виде.

**E2. Термин конфликтует с более общим правилом** — система показывает оба
правила и применяет более специфичное (точное совпадение приоритетнее
подстроки).

**E3. Пересинтез затрагивает опубликованный выпуск** *(шаг 8)* — требуется
подтверждение продюсера: опубликованная дорожка меняется только с его
решения. Редактор не может незаметно подменить то, что уже увидел зритель.

### Постусловия

Успех: правило действует для всех будущих синтезов проекта; затронутые
сегменты пересинтезированы; машинные варианты сохранены как предыдущие ревизии.

## UC-03 — Ручная правка отклонённого выпуска

**Уровень:** цель пользователя · **Основной актор:** Технический редактор

**Предусловия:** выпуск отклонён автоконтролем, список проблемных сегментов
сформирован.

**Триггер:** редактор получает задачу на правку.

### Основной сценарий

1. Редактор открывает выпуск и видит список сегментов с превышением метрик.
2. Редактор прослушивает сегмент вместе с оригиналом.
3. Редактор определяет тип дефекта: перевод, произношение или тайминг.
4. Редактор вносит правку — текст, транскрипция или границы сегмента.
5. Система создаёт новую ревизию сегмента, сохраняя машинный вариант.
6. Редактор повторяет шаги 2–5 для всех проблемных сегментов.
7. Редактор запускает пересинтез изменённых сегментов.
8. Система пересобирает дорожку и пересчитывает метрики.
9. Редактор передаёт выпуск на MOS-тест
   (см. [UC-04](#uc-04--проведение-mos-теста)).

### Альтернативные потоки

**A1. Дефект системный, а не разовый** *(шаг 3)* — редактор заводит запись в
глоссарий вместо правки конкретного сегмента, далее
[UC-02](#uc-02--фонетическая-коррекция-через-глоссарий).

**A2. Откат правки** *(шаг 5)* — редактор возвращается к предыдущей ревизии;
история изменений сохраняется целиком.

**A3. Метрики после правки всё ещё за порогом** *(шаг 8)* — редактор
возвращается к шагу 1 с обновлённым списком проблем.

### Исключения

**E1. Правка тайминга пересекает соседний сегмент** *(шаг 4)* — изменение
отклоняется с указанием конфликтующего сегмента.

**E2. Пересинтез не улучшил метрики** *(шаг 8)* — если после исправления
причины метрики не изменились, выпуск эскалируется на смену голосового
профиля или провайдера. Второй круг правок тех же сегментов не запускается —
модель процесса явно ведёт в другую ветку.

**E3. Параллельная правка двумя редакторами** — сегмент блокируется на время
редактирования; второй редактор видит, кто его держит.

### Постусловия

Успех: изменённые сегменты имеют новые ревизии, дорожка пересобрана, метрики
пересчитаны, выпуск готов к MOS-тесту. Неуспех: выпуск эскалирован на смену
конфигурации.

## UC-04 — Проведение MOS-теста

**Уровень:** цель пользователя · **Основной актор:** Продюсер
**Заинтересованы:** заказчик (гарантия качества), редактор (объективная оценка работы)

**Предусловия:** выпуск прошёл автоконтроль, доступно не менее пяти асессоров.

**Триггер:** продюсер запускает приёмку выпуска.

### Основной сценарий

1. Продюсер запускает MOS-тест по выпуску.
2. Система формирует выборку не менее 20 сегментов, включая пограничные по
   метрикам.
3. Система рассылает задания асессорам.
4. Асессор прослушивает сегмент и ставит оценку от 1 до 5.
5. Асессор не видит оценок других участников и значений метрик.
6. Система собирает оценки и рассчитывает среднее с доверительным интервалом.
7. При MOS ≥ 4.0 выпуск получает статус «принят».
8. Продюсер публикует выпуск
   (см. [UC-05](#uc-05--публикация-дорожки-на-видеохостинге)).

### Альтернативные потоки

**A1. Расширение выборки** *(шаг 2)* — продюсер увеличивает число сегментов
для спорного выпуска.

**A2. Асессор пропускает сегмент** — сегмент передаётся другому асессору,
пропуск не засчитывается как оценка.

### Исключения

**E1. Оценок меньше пяти на сегмент** *(шаг 6)* — MOS помечается как
предварительный, приёмка не считается пройденной. Публикация недоступна.

**E2. MOS ниже 4.0** *(шаг 7)* — выпуск эскалируется на смену голосового
профиля или провайдера для этого языка. Возврат в правку сегментов не
предусмотрен: причина системная.

**E3. Большой разброс оценок** — при доверительном интервале шире 0.8
система требует расширить выборку до принятия решения. Среднее по
противоречивым оценкам не является основанием для приёмки.

### Постусловия

Успех: выпуск принят, MOS зафиксирован в отчёте по языку и провайдеру.
Неуспех: выпуск эскалирован, причина зафиксирована в сравнении провайдеров.

### Нефункциональные требования

- Асессор не видит ни метрик, ни имени провайдера, ни того, машинный это
  вариант или правленный — иначе оценка перестаёт быть слепой.
- Один асессор оценивает не более 30 сегментов за сессию: дальше начинается
  усталость слуха и оценки теряют разрешающую способность.

## UC-05 — Публикация дорожки на видеохостинге

**Уровень:** подфункция · **Основной актор:** Система

**Предусловия:** выпуск принят, у системы есть права на изменение видео.

**Триггер:** продюсер нажимает «Опубликовать» либо принятие выпуска
запускает автопубликацию.

### Основной сценарий

1. Система проверяет статус приёмки выпуска.
2. Система загружает дорожку на хостинг через API.
3. Система дожидается завершения асинхронной обработки на стороне хостинга.
4. Система привязывает дорожку к видео как аудиотрек целевого языка.
5. Система фиксирует факт публикации и уведомляет продюсера.

### Альтернативные потоки

**A1. Замена ранее опубликованной дорожки** *(шаг 4)* — предыдущая версия
архивируется, а не удаляется; откат возможен.

**A2. Хостинг обрабатывает загрузку дольше ожидаемого** *(шаг 3)* — система
переходит в режим опроса статуса, выпуск остаётся в состоянии «публикуется».

### Исключения

**E1. Выпуск не прошёл приёмку** *(шаг 1)* — публикация отклоняется. Обойти
проверку не может ни одна роль: ограничение реализовано на стороне сервера,
а не скрытием кнопки.

**E2. Хостинг отклонил формат** *(шаг 2)* — дорожка перекодируется в
поддерживаемый формат, попытка повторяется один раз, затем ошибка с
подробностями.

**E3. Потеря связи после загрузки, до подтверждения** *(шаги 3–4)* — при
следующей попытке система проверяет, не загружена ли дорожка уже: публикация
идемпотентна по идентификатору выпуска, дубли аудиотреков не создаются.

### Постусловия

Успех: дорожка доступна зрителю, исходная сохранена, факт публикации записан.
Неуспех: выпуск в статусе «принят, не опубликован», причина зафиксирована.

## UC-06 — Подключение и сравнение провайдера

**Уровень:** цель пользователя · **Основной актор:** Продюсер

**Предусловия:** есть учётные данные нового провайдера и эталонный набор
контента.

**Триггер:** необходимость снизить стоимость, добавить язык или заменить
провайдера с нестабильным качеством.

### Основной сценарий

1. Продюсер подключает провайдера, указывая учётные данные и поддерживаемые
   языки.
2. Система проверяет соединение и получает список доступных голосов.
3. Продюсер запускает пилот на эталонном наборе из 10 роликов.
4. Система дублирует набор новым провайдером параллельно с текущим.
5. Система считает WER, рассинхрон, стоимость минуты и время обработки по
   обоим.
6. Асессоры проводят слепой MOS-тест по обоим вариантам.
7. Продюсер сравнивает результаты в сводной таблице.
8. Продюсер назначает провайдера на конкретные языки.

### Альтернативные потоки

**A1. Провайдер лучше только на части языков** *(шаг 8)* — назначение
выполняется по языкам, а не целиком. Это ожидаемый исход, а не компромисс.

**A2. Постепенный переход** — новый провайдер включается на доле трафика,
метрики сравниваются на реальных выпусках.

### Исключения

**E1. Провайдер не отдаёт тайм-коды в STT** *(шаг 2)* — подключение
отклоняется: без тайм-кодов невозможно выравнивание, это блокирующее
требование, а не пожелание.

**E2. Провайдер не поддерживает SSML** — подключение возможно, но система
предупреждает, что фонетическая коррекция для него будет ограничена
подстановкой в текст.

**E3. Условия обработки данных не соответствуют договору с заказчиком** —
подключение блокируется до юридического согласования. Проверка выполняется
до пилота, а не после.

### Постусловия

Успех: провайдер подключён и назначен на языки, где он объективно лучше;
результаты сравнения сохранены и доступны для последующих решений.

### Нефункциональные требования

- Смена провайдера не требует изменений в пайплайне — только конфигурации:
  это проверяется тем, что подключение выполняется без релиза.
- Эталонный набор фиксирован и не меняется между сравнениями, иначе
  результаты несопоставимы.
