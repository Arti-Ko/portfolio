# User Stories — B2B-платформа управления стройпроектами

4 эпика, 17 историй. Приоритизация по MoSCoW, оценка в story points,
критерии приёмки в Gherkin.

Истории написаны по непротиворечивой версии требований — исходные
конфликты и принятые решения зафиксированы в
[requirements-log.md](requirements-log.md).

### Порядок поставки

Сначала — сквозной путь от ТЗ до приёмки первого этапа на одном проекте.
Не полный набор функций каждого экрана, а один проход целиком: именно он
проверяет главную гипотезу — готовы ли обе стороны вести проект в единой
системе.

# EP-01. Техническое задание и тендер

## US-01.1 — Создание технического задания

**Как** клиент, **я хочу** описать задачу в свободной форме с
приложениями, **чтобы** не разбираться в строительной терминологии.

`Must` · `8 SP` · зависимостей нет

```gherkin
Функция: Создание ТЗ

  Сценарий: Заполнение задания
    Когда клиент указывает название, описание задачи, бюджетный диапазон
      и желаемые сроки
    И прикладывает файлы
    Тогда проект создаётся в статусе "черновик"
    И направляется менеджеру на согласование

  Сценарий: Ограничение на приложения
    Когда клиент прикладывает файлы сверх допустимого количества
    Тогда загрузка отклоняется с указанием ограничения

  Сценарий: Бюджет указан диапазоном
    Когда клиент заполняет бюджет
    Тогда поле принимает диапазон "от" и "до", а не одно значение
```

## US-01.2 — Валидация ТЗ менеджером

**Как** менеджер платформы, **я хочу** править и уточнять ТЗ до открытия
тендера, **чтобы** подрядчики считали смету по одному и тому же объёму.

`Must` · `8 SP` · после US-01.1

```gherkin
Функция: Валидация задания

  Сценарий: Менеджер уточняет ТЗ
    Когда менеджер открывает проект в статусе "черновик"
    Тогда он может просматривать и редактировать поля ТЗ

  Сценарий: Возврат клиенту на уточнение
    Дано ТЗ содержит недостаточно информации
    Когда менеджер возвращает его клиенту
    Тогда проект остаётся в статусе "черновик"
    И клиент видит, что именно требуется дополнить

  Сценарий: Открытие тендера
    Когда менеджер подтверждает готовность ТЗ
    Тогда проект переходит в статус "тендер"
    И действие открытия тендера доступно только из карточки проекта
```

## US-01.3 — Приглашение подрядчиков

**Как** менеджер платформы, **я хочу** приглашать подрядчиков вручную,
**чтобы** в тендере участвовали только подходящие под задачу.

`Must` · `8 SP` · после US-01.2

```gherkin
Функция: Закрытый тендер

  Сценарий: Приглашение из аккредитованного пула
    Когда менеджер приглашает подрядчиков
    Тогда они получают приглашение со сроком подачи предложения
    И проект не появляется в публичном доступе

  Сценарий: Подрядчик с истёкшей аккредитацией
    Дано срок аккредитации подрядчика истёк
    Когда менеджер формирует список приглашений
    Тогда этот подрядчик недоступен для приглашения

  Сценарий: Подрядчик видит только свои приглашения
    Когда подрядчик открывает кабинет
    Тогда он видит приглашения, адресованные ему
    И не видит других участников тендера
```

## US-01.4 — Подача коммерческого предложения

**Как** подрядчик, **я хочу** подать предложение с разбивкой по этапам,
**чтобы** клиент понимал структуру работ и цены.

`Must` · `8 SP` · после US-01.3

```gherkin
Функция: Подача предложения

  Сценарий: Предложение с этапами
    Когда подрядчик указывает общую стоимость, срок и разбивку по этапам
    Тогда предложение отправляется менеджеру на проверку

  Сценарий: Сумма этапов не сходится с общей
    Дано сумма этапов отличается от указанной общей стоимости
    Когда подрядчик отправляет предложение
    Тогда система показывает расхождение и требует исправить

  Сценарий: Срок подачи истёк
    Дано срок подачи предложения прошёл
    Когда подрядчик пытается отправить предложение
    Тогда отправка отклоняется
```

## US-01.5 — Сравнение и выбор подрядчика

**Как** клиент, **я хочу** сравнить предложения на одном экране, **чтобы**
выбрать осознанно, а не по одной цифре.

`Must` · `7 SP` · после US-01.4

```gherkin
Функция: Выбор подрядчика

  Сценарий: Короткий список
    Когда клиент открывает вкладку тендера
    Тогда он видит проверенные менеджером предложения
    И по каждому — подрядчика, итоговую смету и срок

  Сценарий: Детали предложения
    Когда клиент открывает детали
    Тогда он видит разбивку по этапам со стоимостью и сроками

  Сценарий: Выбор формирует этапы проекта
    Когда клиент выбирает подрядчика
    Тогда этапы выбранного предложения становятся рабочей таблицей этапов
    И проект переходит в статус "в работе"
```

# EP-02. Этапы и приёмка

## US-02.1 — Таблица этапов проекта

**Как** участник проекта, **я хочу** видеть все этапы со статусами и
суммами, **чтобы** понимать, где находится проект.

`Must` · `8 SP` · после US-01.5

```gherkin
Функция: Таблица этапов

  Сценарий: Отображение этапов
    Когда участник открывает вкладку этапов
    Тогда он видит название, статус, сумму, плановые сроки и доступное действие
    И видит общую сумму проекта

  Сценарий: Действие зависит от статуса и роли
    Дано этап в статусе "требует оплаты"
    Когда таблицу открывает клиент
    Тогда ему доступно действие оплаты
    И подрядчику это действие недоступно
```

## US-02.2 — Начало работы по этапу

**Как** подрядчик, **я хочу** начинать работу только после блокировки
средств, **чтобы** не работать без гарантии оплаты.

`Must` · `8 SP` · после US-02.1

```gherkin
Функция: Старт этапа

  Сценарий: Работа доступна после оплаты
    Дано средства по этапу заблокированы
    Когда подрядчик открывает этап
    Тогда ему доступно действие начала работы

  Сценарий: Работа недоступна без оплаты
    Дано этап в статусе "требует оплаты"
    Когда подрядчик открывает этап
    Тогда действие начала работы недоступно
```

## US-02.3 — Сдача этапа с отчётом

**Как** подрядчик, **я хочу** сдавать работу с фото- и видеофиксацией,
**чтобы** подтвердить выполнение без выезда клиента на объект.

`Must` · `13 SP` · после US-02.2

```gherkin
Функция: Сдача этапа

  Сценарий: Запрос приёмки с отчётом
    Когда подрядчик запрашивает приёмку и прикладывает фото- или видеоотчёт
    Тогда этап переходит в статус "на проверке"
    И менеджер получает уведомление

  Сценарий: Запрос приёмки без отчёта
    Когда подрядчик пытается сдать этап без приложений
    Тогда система требует приложить отчёт

  Сценарий: Отчёт доступен обеим сторонам
    Когда этап переходит на проверку
    Тогда отчёт виден и менеджеру, и клиенту
```

## US-02.4 — Проверка и подтверждение приёмки

**Как** клиент, **я хочу** подтверждать приёмку после проверки менеджером,
**чтобы** не оценивать качество работ самостоятельно.

`Must` · `8 SP` · после US-02.3

```gherkin
Функция: Двухконтурная приёмка

  Сценарий: Менеджер проверяет первым
    Дано этап в статусе "на проверке"
    Когда менеджер подтверждает соответствие объёму
    Тогда клиенту становится доступно подтверждение приёмки

  Сценарий: Клиент подтверждает
    Когда клиент подтверждает приёмку
    Тогда менеджеру становится доступно действие выплаты

  Сценарий: Клиент не может принять до проверки менеджером
    Дано менеджер ещё не проверил отчёт
    Когда клиент открывает этап
    Тогда подтверждение приёмки недоступно
```

## US-02.5 — Возврат этапа на доработку

**Как** менеджер платформы, **я хочу** возвращать этап с замечаниями,
**чтобы** подрядчик исправил, а не спорил в переписке.

`Must` · `5 SP` · после US-02.4

```gherkin
Функция: Доработка

  Сценарий: Возврат с указанием причины
    Когда менеджер возвращает этап на доработку
    Тогда он указывает замечания
    И этап переходит в статус "на доработке"

  Сценарий: Новый цикл сохраняет историю
    Когда подрядчик снова берёт этап в работу
    Тогда открывается новый цикл этапа
    И отчёт и замечания прошлого цикла сохраняются

  Сценарий: Число возвратов видно
    Когда участник открывает этап
    Тогда он видит, сколько циклов доработки было
```

# EP-03. Финансовый контур

## US-03.1 — Оплата этапа и блокировка средств

**Как** клиент, **я хочу** чтобы деньги блокировались, а не уходили
подрядчику сразу, **чтобы** платить за результат.

`Must` · `13 SP` · после US-02.1

```gherkin
Функция: Блокировка средств

  Сценарий: Оплата этапа
    Когда клиент оплачивает этап
    Тогда средства блокируются на эскроу-счёте
    И этап переходит в статус "оплачен"

  Сценарий: Средства помечены как заблокированные
    Когда этап оплачен
    Тогда обе стороны видят, что средства зарезервированы, а не переведены

  Сценарий: Оплата уже оплаченного этапа
    Когда предпринимается попытка оплатить этап повторно
    Тогда действие блокируется
```

## US-03.2 — Выплата подрядчику

**Как** подрядчик, **я хочу** получать оплату сразу после подтверждения
приёмки, **чтобы** не ждать отдельного согласования бюджета.

`Must` · `8 SP` · после US-03.1, US-02.4

```gherkin
Функция: Выплата

  Сценарий: Выплата после приёмки
    Дано клиент подтвердил приёмку этапа
    Когда менеджер инициирует выплату
    Тогда средства переводятся подрядчику
    И этап переходит в статус "принят и оплачен"

  Сценарий: Выплата инициируется человеком
    Дано клиент подтвердил приёмку
    Когда никто не инициировал выплату
    Тогда средства остаются заблокированными
    И перевод не выполняется автоматически

  Сценарий: Выплата до приёмки невозможна
    Дано этап не принят клиентом
    Когда менеджер пытается инициировать выплату
    Тогда действие блокируется
```

## US-03.3 — Сверка состояния средств

**Как** менеджер платформы, **я хочу** видеть расхождения между статусом
этапа и состоянием средств, **чтобы** ловить сбои до того, как о них
скажет клиент.

`Should` · `5 SP` · после US-03.2

```gherkin
Функция: Сверка

  Сценарий: Расхождение обнаружено
    Дано этап помечен оплаченным, а средства не заблокированы
    Когда выполняется сверка
    Тогда расхождение отображается менеджеру

  Сценарий: Внешний провайдер недоступен
    Когда операция с эскроу не проходит
    Тогда статус этапа не меняется
    И пользователь видит понятную причину
```

# EP-04. Коммуникация и прозрачность

## US-04.1 — Чат проекта

**Как** участник проекта, **я хочу** обсуждать работу там же, где ведётся
проект, **чтобы** переписка не терялась в мессенджерах.

`Must` · `8 SP` · после US-01.5

```gherkin
Функция: Чат проекта

  Сценарий: Общий чат сторон
    Когда участник открывает вкладку коммуникации
    Тогда он видит переписку клиента, подрядчика и платформы
    И сообщения платформы визуально выделены

  Сценарий: Вложения в чате
    Когда участник прикладывает файл
    Тогда он доступен остальным участникам проекта

  Сценарий: Чат привязан к проекту
    Когда участник открывает другой проект
    Тогда он видит отдельный чат этого проекта
```

## US-04.2 — Документы проекта

**Как** участник, **я хочу** видеть все файлы проекта в одном месте,
**чтобы** не искать их в переписке.

`Must` · `5 SP` · после US-04.1

```gherkin
Функция: Документы

  Сценарий: Список документов
    Когда участник открывает вкладку документов
    Тогда он видит ТЗ, предложения, отчёты по этапам и договор

  Сценарий: Договор как файл
    Когда договор загружен
    Тогда он доступен во вкладке документов
    И отдельных экранов подписания в системе нет
```

## US-04.3 — История действий

**Как** менеджер платформы, **я хочу** видеть журнал изменений, **чтобы**
разбирать спорные ситуации по фактам.

`Must` · `5 SP` · зависимостей нет

```gherkin
Функция: История действий

  Сценарий: Журнал изменений
    Когда менеджер открывает историю проекта
    Тогда он видит изменения статусов, сумм, сроков с автором и временем

  Сценарий: Финансовые операции в журнале
    Когда выполняется блокировка или выплата
    Тогда операция фиксируется в истории

  Сценарий: Журнал доступен только менеджеру
    Когда клиент или подрядчик открывает проект
    Тогда полный журнал действий им недоступен
```

## US-04.4 — Приоритет и архив проектов

**Как** менеджер платформы, **я хочу** расставлять приоритеты и убирать
завершённое, **чтобы** работать со списком из сотни проектов.

`Should` · `6 SP` · после US-02.1

```gherkin
Функция: Управление списком проектов

  Сценарий: Приоритет задаётся вручную
    Когда менеджер выбирает приоритет проекта
    Тогда он отображается в общем списке
    И список можно фильтровать по нему

  Сценарий: Архивирование завершённого проекта
    Дано все этапы приняты и оплачены
    Когда клиент архивирует проект
    Тогда он скрывается из активного списка
    И доступен через фильтр архива

  Сценарий: Архивирование незавершённого проекта
    Дано в проекте есть неоплаченные этапы
    Когда предпринимается попытка архивировать
    Тогда действие блокируется
```

## Definition of Ready

История берётся в спринт, если: определён допустимый переход состояния и
кто его выполняет; описано поведение при недоступности эскроу-провайдера;
проверено соответствие журналу решений; указано, что попадает в историю
действий.

## Definition of Done

Сценарии Gherkin покрыты автотестами; проверены недопустимые переходы
состояний; проверено, что финансовая операция не выполняется без
подтверждения человеком; поведение при сбое внешнего провайдера проверено
намеренным отказом.
