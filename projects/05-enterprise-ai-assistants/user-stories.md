# User Stories — Enterprise AI-помощники

4 эпика, 18 историй. Приоритизация по MoSCoW, оценка в story points,
критерии приёмки в Gherkin.

## Карта эпиков

| Эпик | Название | Историй | SP | Ценность |
|---|---|---|---|---|
| EP-01 | Поиск по нормативной базе | 5 | 42 | Первый продукт к запуску: понятная ценность, измеримая экономия |
| EP-02 | Согласование медицинских назначений | 5 | 55 | Самый дорогой и самый рискованный продукт программы |
| EP-03 | Проверка контрагентов | 4 | 34 | Убирает ручной обход трёх десятков сайтов |
| EP-04 | Платформа и эксплуатация | 4 | 29 | Делает остальные три продукта поддерживаемыми |

**Итого: 160 SP.**

### Порядок поставки

Программа запускается с эпика EP-01 не потому, что он важнее, а потому что
он дешевле всего проверяет главную гипотезу: работает ли локальная модель
на русскоязычной доменной лексике заказчика. Если поиск по ЛНА не выходит
на приемлемое качество, медицинский продукт с той же инфраструктурой тем
более не выйдет — и это лучше узнать за 11 млн, чем за 45.

Приёмочный корпус из размеченных вопросов и эталонных ответов собирается
до начала разработки. Без него нельзя ни принять историю, ни сравнить
модели, ни доказать заказчику достижение метрики.

# EP-01. Поиск по нормативной базе

## US-01.1 — Ответ со ссылками на источник

**Как** сотрудник, **я хочу** получать ответ с указанием конкретных пунктов
документов, **чтобы** сослаться на них в работе и проверить, что система
не выдумала.

`Must` · `13 SP` · зависимостей нет

```gherkin
Функция: Ответ с обоснованием

  Сценарий: Ответ на вопрос, покрытый базой
    Когда сотрудник задаёт вопрос по регламенту урегулирования убытков
    Тогда система отвечает текстом
    И приводит ссылки на пункты документов, из которых взят ответ
    И для каждой ссылки указаны номер документа, пункт и редакция

  Сценарий: Утверждение без подтверждения источником
    Дано модель сформулировала обобщение, не подтверждённое найденными фрагментами
    Когда формируется ответ
    Тогда обобщение не выдаётся как утверждение
    И пользователю показываются найденные цитаты

  Сценарий: Ответа в базе нет
    Дано релевантных фрагментов не найдено
    Когда система формирует ответ
    Тогда она сообщает, что ответа в базе нет
    И не генерирует правдоподобный текст
```

## US-01.2 — Гибридный поиск

**Как** сотрудник, **я хочу** находить документ и по смыслу вопроса, и по
точному номеру, **чтобы** не подбирать формулировку под поисковый движок.

`Must` · `8 SP` · после US-01.1

```gherkin
Функция: Гибридный поиск

  Сценарий: Смысловой запрос
    Когда сотрудник спрашивает "что делать при отказе в выплате"
    Тогда находятся документы по теме, даже если этой формулировки в них нет

  Сценарий: Запрос по точному идентификатору
    Когда сотрудник указывает номер внутреннего приказа
    Тогда именно этот документ находится первым

  Сценарий: Смешанный запрос
    Когда сотрудник спрашивает о содержании конкретного приказа
    Тогда результаты объединяют оба механизма поиска
    И порядок определяется переранжированием
```

## US-01.3 — Разграничение доступа к документам

**Как** владелец документа, **я хочу** чтобы закрытые ЛНА не попадали в
ответы сотрудникам без доступа, **чтобы** система не стала обходным путём
к конфиденциальной информации.

`Must` · `8 SP` · после US-01.1

```gherkin
Функция: Разграничение доступа

  Сценарий: Область поиска сужается по правам
    Дано у сотрудника нет доступа к документам по тарифообразованию
    Когда он задаёт вопрос, ответ на который есть только в них
    Тогда система сообщает, что ответа в доступной ему области нет
    И не раскрывает содержание закрытых документов

  Сценарий: Права проверяются до поиска
    Когда выполняется запрос
    Тогда закрытые документы не попадают даже в промежуточную выборку

  Сценарий: Изменение прав применяется сразу
    Дано сотруднику открыли доступ к разделу
    Когда он повторяет прежний запрос
    Тогда ответ формируется с учётом новых документов
```

## US-01.4 — Сравнение редакций документа

**Как** методолог, **я хочу** видеть, что изменилось между редакциями ЛНА,
**чтобы** понимать последствия правок без построчного сличения.

`Should` · `8 SP` · после US-01.2

```gherkin
Функция: Сравнение редакций

  Сценарий: Различия между двумя редакциями
    Когда пользователь выбирает две редакции документа
    Тогда система показывает добавленные, удалённые и изменённые пункты
    И формулирует сводку смысловых изменений

  Сценарий: Ответ учитывает дату
    Когда пользователь задаёт вопрос с указанием даты
    Тогда ответ формируется по редакции, действовавшей на эту дату
```

## US-01.5 — Поиск противоречий в базе

**Как** методолог, **я хочу** находить нормы, противоречащие друг другу,
**чтобы** приводить базу в порядок, а не узнавать о конфликте от сотрудника.

`Could` · `5 SP` · после US-01.4

```gherkin
Функция: Поиск противоречий

  Сценарий: Конфликтующие требования
    Когда запускается проверка по выбранной теме
    Тогда система показывает пары пунктов с расходящимися требованиями
    И приводит цитаты обоих

  Сценарий: Ложное срабатывание
    Когда методолог помечает найденное противоречие как мнимое
    Тогда пара исключается из последующих отчётов
```

# EP-02. Согласование медицинских назначений

## US-02.1 — Распознавание протокола

**Как** система, **я хочу** извлекать из протокола диагнозы, услуги и
назначения, **чтобы** проверять их автоматически.

`Must` · `13 SP` · зависимостей нет

```gherkin
Функция: Извлечение данных протокола

  Сценарий: Протокол в виде структурированного документа
    Когда протокол поступает в машиночитаемом виде
    Тогда извлекаются диагнозы по МКБ-10, коды услуг и количество

  Сценарий: Скан с сохранением структуры
    Дано протокол пришёл сканом с таблицей назначений
    Когда выполняется распознавание
    Тогда строки таблицы извлекаются как отдельные назначения
    И связь услуги с количеством не теряется

  Сценарий: Низкое качество скана
    Дано уверенность распознавания ниже порога
    Когда формируется результат
    Тогда протокол направляется врачу-эксперту на ручное чтение
    И автоматический отказ не выдаётся
```

## US-02.2 — Проверка по клиническим рекомендациям

**Как** врач-эксперт, **я хочу** чтобы система сверяла назначение с
действующей редакцией рекомендаций, **чтобы** решение было защищаемым.

`Must` · `13 SP` · после US-02.1

```gherkin
Функция: Проверка по правилам

  Сценарий: Назначение соответствует рекомендации
    Дано услуга предусмотрена клинической рекомендацией по диагнозу
    Когда выполняется проверка
    Тогда назначение помечается соответствующим
    И указывается пункт рекомендации

  Сценарий: Учитывается редакция на дату назначения
    Дано рекомендация обновилась после даты назначения
    Когда выполняется проверка
    Тогда применяется редакция, действовавшая на дату назначения

  Сценарий: Услуга вне покрытия полиса
    Дано услуга предусмотрена рекомендацией, но не входит в покрытие
    Когда выполняется проверка
    Тогда причиной отказа указывается условие полиса, а не рекомендация
```

## US-02.3 — Ветка спорных случаев

**Как** пациент, **я хочу** чтобы в неоднозначной ситуации решение
принимал врач, **чтобы** автомат не отказал мне в лечении по формальному
признаку.

`Must` · `13 SP` · после US-02.2

```gherkin
Функция: Спорные случаи

  Сценарий: Неоднозначное соответствие
    Дано назначение частично соответствует рекомендации
    Когда формируется вердикт
    Тогда случай направляется врачу-эксперту
    И система показывает ему найденные аргументы за и против

  Сценарий: Решение эксперта фиксируется
    Когда врач-эксперт принимает решение
    Тогда оно сохраняется с указанием автора и обоснования
    И имеет тот же статус, что и автоматическое

  Сценарий: Автомат не отказывает при неуверенности
    Дано уверенность в классификации ниже порога
    Когда формируется вердикт
    Тогда автоматический отказ не выдаётся ни при каких условиях
```

## US-02.4 — Мотивированный отказ

**Как** клиника, **я хочу** получать отказ со ссылкой на конкретное
правило, **чтобы** понимать, что исправить, и иметь возможность оспорить.

`Must` · `8 SP` · после US-02.2

```gherkin
Функция: Мотивированный отказ

  Сценарий: Состав отказа
    Когда формируется отказ
    Тогда он содержит перечень отклонённых позиций
    И по каждой указано нарушенное правило с цитатой
    И указан порядок оспаривания

  Сценарий: Несколько оснований
    Дано позиция нарушает два правила
    Когда формируется отказ
    Тогда перечислены оба основания

  Сценарий: Частичное согласование
    Дано часть позиций протокола соответствует правилам
    Когда формируется решение
    Тогда согласованные позиции согласуются
    И отказ выносится только по остальным
```

## US-02.5 — Метрики качества согласования

**Как** руководитель направления, **я хочу** измерять точность системы на
эталонном наборе, **чтобы** решать, можно ли снижать долю ручной проверки.

`Must` · `8 SP` · после US-02.3

```gherkin
Функция: Измерение качества

  Сценарий: Прогон на эталонном наборе
    Когда запускается проверка на размеченных врачами протоколах
    Тогда рассчитываются доля верных согласований и верных отказов
    И отдельно считается доля протоколов, ушедших к эксперту

  Сценарий: Ошибочный отказ весит больше
    Когда формируется сводная оценка
    Тогда неверный отказ учитывается с большим весом,
      чем неверное согласование

  Сценарий: Регрессия блокирует выпуск
    Дано новая версия правил ухудшила точность
    Когда запускается прогон
    Тогда изменение отклоняется с указанием затронутых сценариев
```

# EP-03. Проверка контрагентов

## US-03.1 — Сводный паспорт контрагента

**Как** сотрудник службы безопасности, **я хочу** получать один отчёт
вместо обхода 30 сайтов, **чтобы** тратить время на анализ, а не на сбор.

`Must` · `13 SP` · зависимостей нет

```gherkin
Функция: Паспорт контрагента

  Сценарий: Сбор из доступных источников
    Когда запускается проверка по идентификатору компании
    Тогда система опрашивает подключённые источники
    И формирует единый отчёт с указанием источника каждого факта
    И указывает дату получения данных

  Сценарий: Часть источников недоступна
    Дано два источника не ответили
    Когда формируется отчёт
    Тогда он выдаётся с явной пометкой, какие проверки не выполнены
    И отсутствие данных не трактуется как отсутствие риска
```

## US-03.2 — Скоринг риска

**Как** сотрудник СБ, **я хочу** видеть обоснованную оценку риска, **чтобы**
приоритизировать проверки, а не читать все отчёты одинаково внимательно.

`Should` · `8 SP` · после US-03.1

```gherkin
Функция: Оценка риска

  Сценарий: Расчёт с раскрытием факторов
    Когда рассчитывается риск
    Тогда показывается итоговая оценка
    И перечислены факторы, повлиявшие на неё, с весами

  Сценарий: Оценка не заменяет решение
    Когда отчёт передаётся сотруднику
    Тогда система не выносит автоматического вердикта о сотрудничестве
```

## US-03.3 — Устойчивость коннекторов

**Как** администратор, **я хочу** чтобы изменение вёрстки источника не
ломало проверку молча, **чтобы** узнавать о проблеме раньше пользователей.

`Must` · `8 SP` · после US-03.1

```gherkin
Функция: Контроль коннекторов

  Сценарий: Источник изменил формат ответа
    Дано структура ответа источника изменилась
    Когда выполняется проверка
    Тогда коннектор помечается сбойным
    И администратор получает уведомление

  Сценарий: Регулярная самопроверка
    Когда запускается плановая проверка коннекторов на эталонных запросах
    Тогда формируется отчёт о состоянии всех источников
```

## US-03.4 — Повторная проверка контрагента

**Как** сотрудник СБ, **я хочу** видеть, что изменилось с прошлой проверки,

`Could` · `5 SP` · после US-03.1

```gherkin
Функция: Сравнение с прошлой проверкой

  Сценарий: Отчёт с дельтой
    Дано контрагент проверялся полгода назад
    Когда запускается повторная проверка
    Тогда отчёт содержит раздел изменений с прошлого раза
```

# EP-04. Платформа и эксплуатация

## US-04.1 — Управление очередью инференса

**Как** администратор, **я хочу** чтобы тяжёлые запросы не блокировали
лёгкие, **чтобы** поиск по базе оставался быстрым при работающем аудите
закупок.

`Must` · `8 SP` · зависимостей нет

```gherkin
Функция: Приоритеты инференса

  Сценарий: Интерактивный запрос вперёд фонового
    Дано выполняется длительный аудит закупочного пакета
    Когда поступает запрос к нормативной базе
    Тогда он обрабатывается, не дожидаясь завершения аудита

  Сценарий: Исчерпание ёмкости
    Дано все слоты инференса заняты
    Когда поступает новый запрос
    Тогда пользователь видит позицию в очереди и оценку времени
    И запрос не отбрасывается молча
```

## US-04.2 — Индексация новой редакции документа

**Как** методолог, **я хочу** чтобы опубликованная редакция ЛНА попадала
в поиск без обращения к администратору, **чтобы** сотрудники не работали
по устаревшей норме.

`Must` · `8 SP` · зависимостей нет

```gherkin
Функция: Индексация

  Сценарий: Публикация новой редакции
    Когда в системе документооборота публикуется новая редакция
    Тогда переиндексируется только этот документ
    И предыдущая редакция остаётся доступной для запросов по дате

  Сценарий: Документ не удалось распознать
    Дано скан нечитаемый
    Когда выполняется индексация
    Тогда документ помечается непроиндексированным
    И методолог видит его в списке проблемных
```

## US-04.3 — Журнал обращений

**Как** служба безопасности, **я хочу** видеть, кто что спрашивал и какие
источники были использованы, **чтобы** разбирать инциденты и подтверждать
корректность работы.

`Must` · `8 SP` · зависимостей нет

```gherkin
Функция: Журналирование

  Сценарий: Полнота записи
    Когда обрабатывается любой запрос
    Тогда фиксируются пользователь, вопрос, использованные источники,
      ответ и модель

  Сценарий: Восстановление контекста задним числом
    Дано прошло полгода
    Когда разбирается спорный случай
    Тогда по журналу восстанавливается, какие редакции документов
      использовались в ответе
```

## US-04.4 — Обратная связь по качеству ответа

**Как** администратор ИИ, **я хочу** собирать оценки пользователей,
**чтобы** видеть проблемные темы и улучшать базу знаний.

`Should` · `5 SP` · после US-01.1

```gherkin
Функция: Обратная связь

  Сценарий: Оценка ответа
    Когда пользователь помечает ответ как неверный
    Тогда сохраняются вопрос, ответ и использованные источники
    И случай попадает в очередь разбора

  Сценарий: Сводка проблемных тем
    Когда администратор открывает отчёт
    Тогда он видит темы с наибольшей долей отрицательных оценок
```

## Definition of Ready

История берётся в спринт, если: определено поведение при неуверенности
модели; указано, что попадает в журнал; для медицинского продукта —
согласовано с врачом-экспертом, какой исход считается верным; подготовлены
примеры в приёмочном корпусе.

## Definition of Done

Сценарии Gherkin покрыты тестами; прогон на приёмочном корпусе не показал
регрессии; проверено поведение при недоступности источника и при
исчерпании ёмкости инференса; изменение отражено в
[threat-model.md](threat-model.md), если затрагивает поверхность атаки.
