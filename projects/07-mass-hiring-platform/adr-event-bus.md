# ADR-01. Синхронизация данных: событийная шина или синхронные вызовы

**Статус:** принято
**Контекст:** пресейл HR-платформы массового найма
**Решение затрагивает:** интеграционный слой, движок воронки, модель данных

---

## Контекст

Платформе нужно обмениваться данными с шестью внешними системами. Основной
предмет спора — синхронизация справочника точек работы: складов,
дарксторов, зон доставки. Кандидат выбирает точку при подаче анкеты,
операционные системы владеют этими данными и меняют их регулярно.

Два обстоятельства делают выбор неочевидным:

**Историческая миграция.** На старте нужно перенести накопленные данные —
десятки тысяч записей о точках и их привязках. Это не поток обновлений, а
единовременная объёмная загрузка, которая должна пройти без остановки
работы обеих сторон.

**Лимиты внешних источников.** Публичный налоговый API допускает два
вызова в минуту. Поток кандидатов в час пик кратно выше. Это не вопрос
оптимизации — это структурное ограничение, определяющее, может ли
кандидат вообще ждать результата проверки на экране.

---

## Рассмотренные варианты

### Вариант 1. Синхронные вызовы

Платформа запрашивает данные у систем-владельцев в момент, когда они нужны.

**За:** простота реализации; всегда актуальные данные; нет дублирования
хранилища; отладка тривиальна.

**Против:** доступность платформы становится произведением доступностей
всех источников. Недоступность справочника точек останавливает подачу
анкет. Историческая миграция превращается в десятки тысяч синхронных
вызовов. Лимит налогового API делает синхронную проверку невозможной в
принципе — не медленной, а именно невозможной при целевом потоке.

### Вариант 2. Событийная шина

Системы-владельцы публикуют события об изменениях, платформа их потребляет
и держит локальную проекцию нужных данных.

**За:** отвязка доступности — платформа работает на локальной проекции,
даже когда источник недоступен. Историческая миграция естественно
ложится на модель: она проигрывается как поток событий. Обратная
публикация событий найма не требует, чтобы потребитель был доступен в
момент найма.

**Против:** данные согласованы в конечном счёте, а не мгновенно; нужна
обработка повторной доставки; появляется локальная копия данных, которой
кто-то должен владеть; выше сложность отладки и эксплуатации.

### Вариант 3. Гибрид

Событийная шина для справочных данных и исходящих событий, синхронные
вызовы для операций, где нужен немедленный ответ.

---

## Решение

**Принят вариант 3: событийная шина для синхронизации точек и публикации
событий найма, синхронные вызовы — только там, где ответ нужен немедленно
и лимиты это позволяют.**

Распределение по интеграциям:

| Интеграция | Способ | Почему так |
|---|---|---|
| Справочник точек работы | События | Историческая миграция и независимость от доступности источника |
| События найма наружу | События через исходящий журнал | Потребители не должны быть доступны в момент найма |
| Публичный налоговый API | Асинхронно, через очередь с лимитом | Два вызова в минуту физически исключают синхронную модель |
| Внутренний налоговый API | Асинхронно, через очередь | Недокументированный контракт: изоляция за адаптером обязательна |
| CRM | Двусторонний обмен: исходящее — событиями, входящее — по расписанию | CRM не умеет публиковать события в нужном формате |
| Медицинский партнёр | Синхронный запрос записи, асинхронный приём заключения | Запись требует немедленного подтверждения слота; заключение приходит через дни |

---

## Последствия

### Положительные

Недоступность любого внешнего источника перестаёт останавливать воронку.
Кандидат заполняет анкету и получает статус «проверка выполняется» вместо
ошибки. Это прямо влияет на конверсию: в массовом найме ошибка на шаге
анкеты означает потерянного кандидата, который не вернётся.

Историческая миграция выполняется тем же механизмом, что и текущая
синхронизация. Не нужен отдельный одноразовый инструмент, который придётся
отлаживать в единственном запуске на боевых данных.

Публикация событий найма через исходящий журнал устраняет расхождение
между состоянием платформы и остальной экосистемы: событие пишется в той
же транзакции, что и изменение данных.

### Отрицательные и что с ними делаем

**Данные точек могут отставать.** Кандидат теоретически может выбрать
точку, закрытую минуту назад. Компенсация: проверка актуальности точки
выполняется синхронно один раз — на шаге оформления, а не при каждом
просмотре списка. Одна проверка в конце воронки вместо сотни в течение.

**Повторная доставка событий.** Обработка идемпотентна по идентификатору
события; повторная доставка не создаёт дублей.

**Сложность эксплуатации.** Нужен мониторинг отставания потребителя и
глубины очередей — метрики, которых не было бы при синхронной модели. Это
принято как цена решения и включено в требования к сопровождению.

**Кандидат не видит мгновенного результата налоговой проверки.** Компенсация
интерфейсом: статус «проверка выполняется» с ожидаемым сроком, уведомление
по завершении. Худший вариант — крутящийся индикатор, за которым стоит
очередь длиной в час.

---

## Что сделало бы решение неверным

Решение стоит пересмотреть, если:

- Владелец справочника точек не сможет публиковать события в приемлемом
  формате — тогда придётся строить синхронизацию по расписанию, и часть
  преимуществ теряется.
- Лимит публичного налогового API будет снят по договору — тогда для
  части сценариев синхронная проверка станет возможной и упростит
  интерфейс.
- Число внешних интеграций сократится до одной-двух — накладные расходы
  событийной модели перестанут окупаться.

Первый пункт был главным риском на этапе пресейла: он зависел от
готовности смежной команды заказчика, а не от нашего решения.
