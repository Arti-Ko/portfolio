# Use Cases — HR-платформа массового найма

Шесть вариантов использования в нотации Коберна. Акцент на поведении
системы при недоступности внешних источников: шесть интеграций означают
шесть способов сломаться, и ни один из них не должен останавливать найм.

| [UC-04](#uc-04--допуск-к-работе-на-транспорте) | Допуск к работе на транспорте | Специалист по БДД | Цель пользователя | Критический |

## Акторы

| Актор | Тип | Интерес |
|---|---|---|
| Кандидат | Первичный, человек | Пройти найм быстро и понимать, что происходит |
| HR-менеджер | Первичный, человек | Управляемый поток без ручного сведения статусов |
| Руководитель отдела | Первичный, человек | Закрытые вакансии в своём подразделении |
| Специалист по БДД | Первичный, человек | Не допустить к управлению того, кого нельзя |
| Офицер безопасности | Первичный, человек | Отсеять неподходящих до дорогих шагов |
| Внешние системы | Вторичный, система | Актуальные данные о нанятых |

## UC-01 — Подача анкеты кандидатом

**Уровень:** цель пользователя · **Основной актор:** Кандидат

**Предусловия:** вакансия открыта, кандидат имеет доступ к порталу.

**Триггер:** кандидат открывает анкету по ссылке из объявления.

**Гарантия минимума:** заполненные блоки анкеты не теряются ни при обрыве
связи, ни при закрытии вкладки.
**Гарантия успеха:** заявка создана, проверки запущены, кандидат видит
свой статус.

### Основной сценарий

1. Кандидат заполняет блок персональных данных.
2. Кандидат выбирает форму занятости: самозанятый или ИП.
3. Система запрашивает комплект документов, соответствующий выбору.
4. Кандидат загружает документы.
5. Система проверяет читаемость и формат файлов.
6. Система ставит налоговую проверку в очередь
   ([UC-02](#uc-02--проверка-налогового-статуса)).
7. Кандидат выбирает точку работы из локальной проекции справочника.
8. Кандидат отправляет анкету.
9. Система создаёт заявку и показывает статус.

### Альтернативные потоки

**A1. Возврат к незавершённой анкете** *(шаги 1–7)* — заполненные блоки
сохранены, кандидат продолжает с прерванного места.

**A2. Смена формы занятости после загрузки документов** *(шаг 2)* —
система показывает, какие документы остаются актуальными, а какие нужно
добавить; повторно загружать всё не требуется.

**A3. Логистическое направление** *(шаг 8)* — заявка после общих проверок
уходит в контур допуска
([UC-04](#uc-04--допуск-к-работе-на-транспорте)).

### Исключения

**E1. Документ нечитаем** *(шаг 5)* — кандидат получает конкретное
указание, что переснять. Общее «файл не подходит» на этом шаге стоит
потерянного кандидата.

**E2. Налоговый статус не подтверждён** *(шаг 6)* — кандидат получает
инструкцию по регистрации статуса, заявка остаётся в ожидании. Отказ здесь
означал бы терять людей, готовых работать, из-за пятиминутной формальности.

**E3. Справочник точек недоступен** *(шаг 7)* — список берётся из
локальной проекции; актуальность выбранной точки проверяется синхронно
один раз, на шаге оформления.

**E4. Кандидат уже подавал заявку** *(шаг 8)* — система показывает
существующую заявку и её статус, дубль не создаётся.

**E5. Кандидат подал заявку и был ранее отклонён** — заявка принимается,
если истёк срок, зафиксированный при отказе; иначе кандидат видит дату,
после которой возможна повторная подача.

### Постусловия

Успех: заявка создана, документы сохранены в зашифрованном виде, проверки
поставлены в очередь, кандидат видит статус и ожидаемые сроки.

### Нефункциональные требования

- Анкета работает на мобильном устройстве: основной канал подачи —
  телефон, а не десктоп.
- Ни один шаг анкеты не ждёт ответа внешней системы синхронно.
- Документы не доступны по прямой ссылке и хранятся зашифрованными.

## UC-02 — Проверка налогового статуса

**Уровень:** подфункция · **Основной актор:** Система

**Предусловия:** кандидат указал форму занятости и идентификационные данные.

**Триггер:** завершение соответствующего блока анкеты.

**Гарантия минимума:** лимит вызовов внешнего API не превышается ни при
каком объёме очереди.

### Основной сценарий

1. Система ставит задачу проверки в очередь.
2. Ограничитель скорости выпускает задачи в пределах лимита источника.
3. Адаптер выполняет запрос к налоговому API.
4. Система сохраняет результат проверки с временем.
5. Система переводит заявку на следующий шаг воронки.
6. Кандидат получает уведомление об изменении статуса.

### Альтернативные потоки

**A1. Статус не подтверждён** *(шаг 4)* — кандидату отправляется
инструкция по регистрации, заявка в состоянии ожидания. Повторная проверка
запускается по сигналу кандидата или по расписанию.

**A2. Запрос к внутреннему API за расширенными данными** — выполняется
отдельной задачей с собственным лимитом.

### Исключения

**E1. Лимит источника исчерпан** *(шаг 2)* — задачи ждут в очереди.
Превышение лимита грозит блокировкой доступа для всей компании, а не
только для одного запроса, — поэтому ограничитель не обходится ни при
каком приоритете.

**E2. Источник вернул ошибку** *(шаг 3)* — задача возвращается в очередь с
нарастающей задержкой.

**E3. Серия отказов подряд** — срабатывает предохранитель, обращения к
источнику приостанавливаются, HR видит перечень отложенных проверок с
причиной. Продолжать долбить недоступный источник — способ получить
блокировку.

**E4. Внутренний API изменил формат ответа** — адаптер фиксирует
несоответствие контракта, задача помечается требующей внимания,
уведомляется команда сопровождения. Недокументированный контракт может
измениться без предупреждения — это принятый риск, для которого
предусмотрено обнаружение.

**E5. Результат приходит после отказа кандидата от вакансии** — результат
сохраняется, действий по заявке не выполняется.

### Постусловия

Успех: результат проверки сохранён, заявка на следующем шаге, кандидат
уведомлён. Неуспех: задача в очереди или отложена, кандидат видит статус
«проверка выполняется», а не ошибку.

## UC-03 — Проверка службой безопасности

**Уровень:** цель пользователя · **Основной актор:** Офицер безопасности

**Предусловия:** налоговый статус подтверждён, документы загружены и
верифицированы.

**Триггер:** заявка переходит на этап проверки безопасности.

### Основной сценарий

1. Офицер открывает заявку из очереди проверки.
2. Система показывает анкету, документы и результаты автоматических проверок.
3. Офицер проводит проверку по внутреннему регламенту.
4. Офицер выносит решение.
5. При положительном решении заявка переходит к тестированию и
   собеседованию.

### Альтернативные потоки

**A1. Запрос дополнительных документов** *(шаг 3)* — заявка возвращается
кандидату с указанием, что предоставить; срок ожидания фиксируется.

**A2. Расхождение данных документа и анкеты** — заявка направляется HR на
разбор до вынесения решения: расхождение может быть опечаткой, а не
попыткой обмана.

### Исключения

**E1. Отказ по результатам проверки** *(шаг 4)* — офицер обязан указать
причину из справочника. Свободный текст не позволил бы считать статистику
и находить систематические проблемы в источнике кандидатов.

**E2. Истёк срок нахождения в очереди** — заявка эскалируется
руководителю; кандидат получает уведомление о продлении срока
рассмотрения. Молчание в массовом найме означает потерянного кандидата:
он уйдёт к конкуренту, который ответил.

**E3. Офицер открывает заявку вне своей зоны ответственности** — доступ
отклоняется, попытка фиксируется.

### Постусловия

Успех: решение принято и зафиксировано с автором и причиной; при
положительном решении заявка на следующем шаге.

## UC-04 — Допуск к работе на транспорте

**Уровень:** цель пользователя · **Основной актор:** Специалист по БДД
**Заинтересованы:** компания (ответственность за допуск), другие участники движения

**Предусловия:** кандидат прошёл общие проверки, направление —
логистическое.

**Триггер:** заявка поступает в контур допуска.

**Гарантия минимума:** доступ к сменам не открывается без положительного
медицинского заключения и подтверждения человеком.

### Основной сценарий

1. Система предлагает кандидату записаться на медосмотр в партнёрской сети.
2. Кандидат выбирает клинику и слот.
3. Кандидат проходит медосмотр.
4. Партнёр передаёт заключение в портал.
5. Система фиксирует заключение и срок его действия.
6. Специалист по БДД запускает проверку водительского профиля: категория,
   стаж, история нарушений.
7. Система рассчитывает сводную оценку риска.
8. Офицер безопасности подтверждает допуск.
9. Система открывает доступ к сменам и оформляет трудоустройство
   ([UC-05](#uc-05--оформление-и-публикация-события-найма)).

### Альтернативные потоки

**A1. Кандидат уже проходил медосмотр** *(шаг 1)* — при действующем
заключении шаги 1–4 пропускаются.

**A2. Пограничный профиль риска** *(шаг 7)* — решение принимает специалист
с обоснованием; автоматического исхода нет.

### Исключения

**E1. Отрицательное медицинское заключение** *(шаг 4)* — допуск не
выдаётся. Фиксируется причина и дата, после которой возможна повторная
попытка: медицинские противопоказания бывают временными.

**E2. Заключение с истёкшим сроком** *(шаг 5)* — требуется новый
медосмотр. Без проверки срока система однажды выпустит на линию водителя
с просроченным осмотром — и узнает об этом после происшествия.

**E3. Профиль риска вне допустимых пределов** *(шаг 7)* — отказ с
перечнем повлиявших записей. Кандидат имеет право знать, что именно
привело к решению.

**E4. Сервис записи на медосмотр недоступен** *(шаг 2)* — кандидату
предлагается оставить заявку на обратную связь; процесс не обрывается.

**E5. Все проверки пройдены, но офицер отказывает** *(шаг 8)* — отказ
фиксируется отдельно от результатов проверок с обязательным обоснованием.
Смешивать решение человека с результатом автоматической проверки нельзя:
это разные основания с разными последствиями.

### Постусловия

Успех: допуск подтверждён человеком, доступ к сменам открыт одновременно
с оформлением. Неуспех: причина и срок повторной попытки зафиксированы.

## UC-05 — Оформление и публикация события найма

**Уровень:** цель пользователя · **Основной актор:** Система

**Предусловия:** все обязательные проверки пройдены, решение о найме принято.

**Триггер:** HR или руководитель подтверждает найм.

**Гарантия минимума:** не возникает состояния «нанят в платформе,
неизвестен экосистеме» — данные и событие согласованы.

### Основной сценарий

1. Система синхронно проверяет актуальность выбранной точки работы.
2. Система оформляет трудоустройство: тип договора, дата начала, роль.
3. Система записывает изменение данных и событие о найме в одной
   транзакции.
4. Отдельный процесс публикует событие в шину.
5. Смежные системы получают событие и заводят сотрудника у себя.
6. Кандидат получает уведомление о трудоустройстве.

### Альтернативные потоки

**A1. Точка работы закрыта после выбора** *(шаг 1)* — кандидату
предлагается выбрать другую; оформление приостанавливается. Это
единственная синхронная проверка в воронке, и она стоит именно здесь,
а не при каждом просмотре списка.

**A2. Двусторонний обмен с CRM** — исходящее направление идёт событиями,
входящее — регламентной выгрузкой, поскольку CRM не публикует события в
нужном формате.

### Исключения

**E1. Шина недоступна** *(шаг 4)* — событие остаётся в исходящем журнале и
публикуется после восстановления. Найм при этом состоялся: доступность
шины не является условием трудоустройства.

**E2. Сбой между записью данных и публикацией** — благодаря записи в одной
транзакции событие не теряется; процесс публикации подхватывает его
после восстановления.

**E3. Повторная доставка события потребителю** — обработка идемпотентна по
идентификатору события, дубль сотрудника не создаётся.

**E4. Потребитель отклонил событие** — факт фиксируется, команда
сопровождения уведомляется; событие остаётся в журнале до успешной
обработки.

### Постусловия

Успех: сотрудник оформлен, событие опубликовано или гарантированно
доставлено позже, смежные системы синхронизированы.

### Нефункциональные требования

- Событие содержит идентификаторы, роль, точку работы и дату начала —
  без персональных данных сверх необходимого.
- Задержка публикации при доступной шине — секунды; при недоступной
  ограничение отсутствует, но факт задержки виден в мониторинге.

## UC-06 — Ведение потока кандидатов

**Уровень:** цель пользователя · **Основной актор:** HR-менеджер

**Предусловия:** HR авторизован, за ним закреплено направление.

**Триггер:** HR открывает рабочее место.

### Основной сценарий

1. Система показывает поток кандидатов своего направления.
2. HR видит блок заявок, требующих внимания: отклонённые документы,
   расхождения данных, истекающие сроки.
3. HR открывает заявку и просматривает её историю по шагам.
4. HR выполняет действие: запросить документ, назначить собеседование,
   принять решение.
5. Система фиксирует действие и переводит заявку на следующий шаг.

### Альтернативные потоки

**A1. Массовое действие** *(шаг 4)* — HR выбирает несколько заявок на
одном шаге и выполняет действие для всех. В массовом найме поштучная
обработка сотен заявок нереалистична.

**A2. Отчёт по воронке** — HR открывает конверсию по шагам и среднее
время прохождения, сравнивает направления между собой.

**A3. Возврат заявки на предыдущий шаг** — с обязательным указанием
причины.

### Исключения

**E1. Попытка открыть медицинское заключение** *(шаг 3)* — доступ
отклоняется. HR видит результат допуска, но не его медицинское основание:
данные о здоровье относятся к специальной категории и доступны только
специалисту по БДД.

**E2. Заявка изменена другим сотрудником** — при одновременной работе
показывается актуальное состояние, конкурирующее действие отклоняется с
пояснением.

**E3. Отложенные проверки из-за недоступности источника** — HR видит
перечень таких заявок отдельно, с указанием источника и времени
приостановки; заявки не выглядят «зависшими без причины».

### Постусловия

Успех: действия зафиксированы с автором и временем, заявки движутся по
воронке, отложенные проверки видны явно.
