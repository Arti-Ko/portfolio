# C4 — Трекер симптомов для онкопациентов

Машиночитаемый исходник — [`c4/workspace.dsl`](c4/workspace.dsl).

Архитектура MVP спроектирована с одним сквозным ограничением: система не
интерпретирует данные пациента в клиническом смысле. Это не техническое
требование, а условие, при котором продукт не становится медицинским
изделием — см. [discovery.md](discovery.md).

---

## Уровень 1. Контекст

```mermaid
flowchart TB
    patient(["👤 Пациент<br/><i>ведёт дневник,<br/>принимает препараты</i>"])
    doctor(["👤 Лечащий врач<br/><i>видит динамику<br/>между приёмами</i>"])
    editor(["👤 Медицинский редактор<br/><i>ведёт справочник<br/>и шаблоны</i>"])

    subgraph boundary[" "]
        system["<b>Трекер симптомов</b><br/><i>Дневник, справочник,<br/>календарь препаратов</i>"]
    end

    push["<b>Сервисы уведомлений</b><br/><i>напоминания<br/>о приёме</i>"]
    pharma["<b>B2B-потребители данных</b><br/><i>обезличенная аналитика —<br/>за пределами MVP</i>"]

    patient -- "отмечает симптомы<br/>и приёмы" --> system
    system -- "показывает справочную<br/>информацию" --> patient
    doctor -- "смотрит динамику" --> system
    editor -- "ведёт контент" --> system
    system -- "отправляет напоминания" --> push
    system -. "агрегированные данные<br/>после MVP" .-> pharma

    classDef person fill:#2b5d8a,stroke:#143349,color:#fff
    classDef corec fill:#1a4d7a,stroke:#0d2840,color:#fff
    classDef ext fill:#4a4f5a,stroke:#2a2e35,color:#fff,stroke-dasharray:4 3
    class patient,doctor,editor person
    class system corec
    class push,pharma ext
    style boundary fill:none,stroke:#888,stroke-dasharray:5 5
```

### Границы MVP

**В скоупе:** дневник симптомов с шаблонами по нозологиям, справочник в
информационно-просветительском формате, календарь приёма препаратов с
напоминаниями, доступ врача к динамике пациента.

**Вне скоупа:** телемедицина и консультации, интерпретация данных с
клиническими рекомендациями пациенту, интеграция с медицинскими
информационными системами, обезличенная выгрузка для B2B.

Последний пункт — не «забыли», а осознанная последовательность: пока не
определён первый B2B-плательщик, требования к выгрузке неизвестны, а
проектировать их наугад дороже, чем добавить позже.

## Уровень 2. Контейнеры

```mermaid
flowchart TB
    patient(["👤 Пациент"])
    doctor(["👤 Лечащий врач"])
    push["<b>Сервисы уведомлений</b>"]

    subgraph sys["Трекер симптомов"]
        mobile["<b>Мобильное приложение</b><br/>iOS, Android<br/><i>дневник, календарь,<br/>справочник</i>"]
        web["<b>Кабинет врача</b><br/>Web<br/><i>динамика пациентов,<br/>флаги</i>"]
        api["<b>Backend API</b><br/><i>записи, схемы приёма,<br/>доступы</i>"]
        rules["<b>Модуль оценки</b><br/><i>шкалы тяжести,<br/>пороги эскалации</i>"]
        scheduler["<b>Планировщик</b><br/><i>окна приёма,<br/>напоминания</i>"]
        content["<b>Контентная служба</b><br/><i>справочник, шаблоны<br/>по нозологиям</i>"]
        db[("<b>БД</b><br/>PostgreSQL<br/><i>записи дневника,<br/>схемы, приверженность</i>")]
    end

    patient --> mobile
    doctor --> web
    mobile -- "REST" --> api
    web -- "REST" --> api
    api -- "SQL" --> db
    api -- "оценка записи" --> rules
    api -- "шаблоны и статьи" --> content
    scheduler -- "ставит напоминания" --> push
    scheduler -- "читает схемы приёма" --> db
    push --> mobile

    classDef person fill:#2b5d8a,stroke:#143349,color:#fff
    classDef container fill:#2f3542,stroke:#171b21,color:#fff
    classDef store fill:#3d5a3d,stroke:#1e2d1e,color:#fff
    classDef ext fill:#4a4f5a,stroke:#2a2e35,color:#fff,stroke-dasharray:4 3
    class patient,doctor person
    class mobile,web,api,rules,scheduler,content container
    class db store
    class push ext
    style sys fill:none,stroke:#888,stroke-dasharray:5 5
```

### Почему так

**Модуль оценки вынесен отдельно от API.** Это место, где проходит
регуляторная граница. Логика «какой симптом при какой нозологии считается
тревожным» должна быть сосредоточена в одном компоненте, который можно
предъявить юристу и медицинскому эксперту целиком, а не искать по коду.
Когда встанет вопрос «интерпретирует ли ваше приложение клинические
данные», ответ должен быть проверяемым.

**Контентная служба отделена от кода.** Справочник и шаблоны симптомов
ведёт медицинский редактор, а не разработчик. Обновление формулировки в
справочнике не должно требовать релиза приложения — в информационно-
просветительском формате именно формулировки определяют регуляторный
статус, и править их нужно быстро.

**Планировщик читает схемы напрямую, минуя API.** Он работает по всем
пациентам массово в фоне; проходить через прикладной API ради этого —
лишний слой без пользы.

**Кабинет врача — отдельный контейнер, а не роль в приложении пациента.**
У врача принципиально другой сценарий: он смотрит не одного пациента, а
список с флагами, и делает это с компьютера.

## Уровень 3. Компоненты модуля оценки

```mermaid
flowchart TB
    api["<b>Backend API</b>"]
    db[("<b>БД</b>")]

    subgraph rules["Модуль оценки"]
        nozology["<b>Профиль нозологии</b><br/><i>какие симптомы отслеживаем<br/>при этом диагнозе</i>"]
        scale["<b>Шкала тяжести</b><br/><i>перевод ответа пациента<br/>в клиническую степень</i>"]
        threshold["<b>Пороги эскалации</b><br/><i>когда поднимать флаг врачу</i>"]
        trend["<b>Анализ динамики</b><br/><i>ухудшение за период,<br/>а не разовый пик</i>"]
        advice["<b>Подбор справки</b><br/><i>какую статью показать —<br/>без рекомендаций по лечению</i>"]
    end

    api --> nozology
    nozology --> scale
    scale --> threshold
    threshold --> trend
    trend --> advice
    threshold --> db

    classDef comp fill:#2f3542,stroke:#171b21,color:#fff
    classDef ext fill:#4a4f5a,stroke:#2a2e35,color:#fff,stroke-dasharray:4 3
    classDef store fill:#3d5a3d,stroke:#1e2d1e,color:#fff
    class nozology,scale,threshold,trend,advice comp
    class api ext
    class db store
    style rules fill:none,stroke:#888,stroke-dasharray:5 5
```

**Анализ динамики важнее порога по одному значению.** Тошнота второй
степени однократно — ожидаемый побочный эффект. Та же тошнота третий день
подряд с нарастанием — повод для врача. Флаг по разовому значению
завалил бы врача ложными срабатываниями, и он перестал бы их читать.

**Подбор справки не даёт рекомендаций по лечению.** Компонент выбирает,
какую статью справочника показать, — и это осознанно самая «глупая» часть
системы. Любая логика вида «при таком симптоме сделайте то-то» переводит
приложение в другой регуляторный статус.

## Модель данных

```mermaid
erDiagram
    PATIENT ||--o{ SYMPTOM_ENTRY : "ведёт"
    PATIENT ||--|| NOZOLOGY_PROFILE : "имеет"
    NOZOLOGY_PROFILE ||--o{ SYMPTOM_TEMPLATE : "определяет"
    SYMPTOM_ENTRY }o--|| SYMPTOM_TEMPLATE : "заполняется по"
    SYMPTOM_ENTRY ||--o| ESCALATION : "может вызвать"
    PATIENT ||--o{ MEDICATION_PLAN : "получает"
    MEDICATION_PLAN ||--o{ INTAKE_EVENT : "порождает"
    PATIENT }o--o{ DOCTOR : "наблюдается у"
    SYMPTOM_TEMPLATE }o--|| ARTICLE : "связан со справкой"

    PATIENT {
        uuid id PK
        string external_ref
        date diagnosis_date
        string consent_status
    }
    NOZOLOGY_PROFILE {
        uuid id PK
        string nozology_code
        string therapy_line
    }
    SYMPTOM_TEMPLATE {
        uuid id PK
        uuid profile_id FK
        string symptom_code
        string scale_type
        int escalation_threshold
    }
    SYMPTOM_ENTRY {
        uuid id PK
        uuid patient_id FK
        uuid template_id FK
        int reported_value
        int graded_severity
        timestamptz recorded_at
    }
    ESCALATION {
        uuid id PK
        uuid entry_id FK
        string reason
        string doctor_action
        timestamptz raised_at
    }
    MEDICATION_PLAN {
        uuid id PK
        uuid patient_id FK
        string drug_ref
        string schedule_rule
        int window_minutes
        date valid_until
    }
    INTAKE_EVENT {
        uuid id PK
        uuid plan_id FK
        timestamptz due_at
        timestamptz confirmed_at
        string status
    }
    DOCTOR {
        uuid id PK
        string speciality
    }
    ARTICLE {
        uuid id PK
        string title
        text body
        string content_version
    }
```

**`SYMPTOM_ENTRY` хранит и то, что отметил пациент, и рассчитанную
степень.** Пациент отвечает на понятный ему вопрос, система переводит
ответ в клиническую шкалу. Хранить только результат перевода — значит
потерять исходные данные при изменении шкалы и лишиться возможности
пересчитать историю.

**`MEDICATION_PLAN.window_minutes` — терапевтическое окно приёма.** Именно
оно определяет, до какого момента напоминание имеет смысл, а после какого
приём считается пропущенным. Значение задаётся схемой терапии, а не общей
настройкой приложения.

**`ARTICLE.content_version`.** Справочник меняется, а показанная пациенту
версия должна быть восстановима: в регулируемой области важно, что именно
человек прочитал в тот день.

**`PATIENT.consent_status` заложен в MVP, хотя выгрузки ещё нет.**
Собирать согласия задним числом у пациентов, часть из которых уже
завершила лечение, невозможно. Поле дешевле добавить сразу, чем потерять
всю накопленную базу для будущей B2B-модели.
