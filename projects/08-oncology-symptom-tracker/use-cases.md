# Use Cases — Трекер симптомов для онкопациентов

Шесть вариантов использования в нотации Коберна. В каждом отдельно
отмечено, где проходит регуляторная граница: система информирует, но не
интерпретирует клинически.

|---|---|---|---|---|

| [UC-02](#uc-02--эскалация-тревожного-симптома) | Эскалация тревожного симптома | Система | Цель пользователя | Критический |

| [UC-04](#uc-04--работа-врача-со-списком-пациентов) | Работа врача со списком | Лечащий врач | Цель пользователя | Критический |
| [UC-05](#uc-05--назначение-и-изменение-схемы-терапии) | Назначение схемы терапии | Лечащий врач | Цель пользователя | Высокий |

## Акторы

| Актор | Тип | Интерес |
|---|---|---|
| Пациент | Первичный, человек | Понимать своё состояние, не пропускать приёмы, быть услышанным врачом |
| Лечащий врач | Первичный, человек | Видеть картину между приёмами, не тонуть в ложных сигналах |
| Медицинский редактор | Первичный, человек | Корректный и юридически безопасный контент |
| Планировщик | Первичный, система | Своевременные напоминания в пределах терапевтического окна |

## UC-01 — Ведение дневника симптомов

**Уровень:** цель пользователя · **Основной актор:** Пациент
**Заинтересованы:** врач (данные для решений), продукт (регулярность ведения — условие любой ценности)

**Предусловия**
1. У пациента указаны диагноз и линия терапии.
2. Для его нозологии загружен профиль симптомов.

**Триггер:** пациент открывает дневник — по напоминанию или сам.

**Гарантия минимума:** запись не теряется, в том числе без сети.
**Гарантия успеха:** запись сохранена, оценена по клинической шкале, при
необходимости флаг поднят врачу.

### Основной сценарий

1. Пациент открывает дневник.
2. Система показывает шаблон симптомов его нозологии.
3. Пациент отмечает состояние по каждому симптому в понятных ему
   формулировках.
4. Система переводит ответы в клиническую шкалу, сохраняя исходные.
5. Модуль оценки сравнивает значения с порогами и динамикой за период.
6. Система показывает справочную информацию по отмеченным симптомам.
7. Запись сохраняется в дневнике.

### Альтернативные потоки

**A1. Быстрая запись** *(шаг 3)* — «самочувствие без изменений»
сохраняется одним действием, без прохождения всех пунктов. Ежедневная
процедура должна занимать минуту, иначе её перестают выполнять.

**A2. Запись задним числом** — пациент вносит пропущенные дни с указанием
фактической даты; пропуск не блокирует текущую запись.

**A3. Работа без сети** — запись сохраняется локально и синхронизируется
позже; эскалация поднимается после синхронизации с фактическим временем
записи.

**A4. Показатель выше порога** *(шаг 5)* — переход к
[UC-02](#uc-02--эскалация-тревожного-симптома).

### Исключения

**E1. Профиль нозологии не назначен** *(шаг 2)* — показывается базовый
набор симптомов, пациенту предлагается уточнить диагноз у врача.
Отказать в ведении дневника нельзя: это оттолкнёт пациента на первом же
экране.

**E2. Пациент отмечает симптом, отсутствующий в шаблоне** — доступен
свободный ввод; такие записи попадают в отчёт для медицинского редактора
как кандидаты на расширение шаблона.

**E3. Пациент интерпретирует справочную статью как назначение** —
предотвращается формулировками: статьи объясняют состояние и указывают,
когда обращаться к врачу, но не предписывают действий. Это регуляторное
требование, а не редакторское предпочтение.

**E4. Запись сделана за дату в будущем** — отклоняется.

### Постусловия

Успех: запись сохранена с исходным ответом и рассчитанной степенью;
динамика обновлена; при превышении порога поднят флаг.

### Нефункциональные требования

- Заполнение стандартной записи — не более минуты.
- Приложение не сообщает пациенту диагноз и не предписывает изменение
  терапии ни в одном сценарии.
- Исходные ответы пациента хранятся отдельно от рассчитанной степени,
  чтобы пережить изменение шкалы.

## UC-02 — Эскалация тревожного симптома

**Уровень:** цель пользователя · **Основной актор:** Система

**Предусловия:** пациент связан с лечащим врачом, пороги для нозологии
заданы.

**Триггер:** запись дневника превысила порог либо выявлено нарастание за
период.

### Основной сценарий

1. Модуль оценки фиксирует превышение порога или нарастающую динамику.
2. Система формирует флаг с указанием симптома, степени и периода.
3. Флаг появляется в кабинете врача в начале списка.
4. Пациент видит, что информация передана врачу.
5. Врач открывает запись, вызвавшую флаг.
6. Врач принимает решение и отмечает флаг обработанным с комментарием.
7. Решение сохраняется в истории пациента.

### Альтернативные потоки

**A1. Нарастание без превышения абсолютного порога** *(шаг 1)* — флаг
поднимается по динамике: три дня усиления значат больше, чем разовый пик.

**A2. Несколько флагов у одного пациента** — объединяются в одну карточку,
чтобы врач видел состояние целиком, а не серию уведомлений.

**A3. Врач связывается с пациентом** — факт контакта фиксируется в
истории вместе с флагом.

### Исключения

**E1. У пациента нет подключённого врача** *(шаг 3)* — флаг не поднимается,
пациенту показывается справочная информация с рекомендацией обратиться в
своё медучреждение. Система не может выступать заменой лечащему врачу.

**E2. Флаг не обработан в установленный срок** — выделяется как
просроченный. Уведомление пациенту о том, что врач не отреагировал, не
отправляется: это создало бы у него ложные ожидания об экстренном канале,
которым продукт не является.

**E3. Ложное срабатывание** — врач отмечает флаг как неинформативный;
такие случаи собираются для калибровки порогов. Врач, заваленный ложными
флагами, перестаёт читать все.

**E4. Запись синхронизирована с задержкой** — флаг поднимается с
указанием фактического времени записи, а не времени синхронизации.

### Постусловия

Успех: врач увидел флаг, принял решение и зафиксировал его; пациент
знает, что информация передана.

**Что процесс намеренно не делает:** не вызывает скорую, не рекомендует
пациенту действий и не заменяет экстренный канал связи. Границы
проговариваются пациенту при подключении.

## UC-03 — Приём препарата по схеме

**Уровень:** цель пользователя · **Основной актор:** Пациент

**Предусловия:** врач назначил схему приёма с терапевтическим окном.

**Триггер:** наступление времени приёма по схеме.

### Основной сценарий

1. Планировщик определяет наступление времени приёма.
2. Пациент получает напоминание.
3. Пациент принимает препарат и отмечает это в приложении.
4. Система фиксирует приём с фактическим временем.
5. Показатель приверженности пересчитывается.

### Альтернативные потоки

**A1. Повтор напоминания** *(шаг 2)* — при отсутствии подтверждения
напоминание повторяется в пределах терапевтического окна и прекращается
после его окончания.

**A2. Отметка задним числом** — пациент подтверждает приём в течение
суток, запись корректируется.

**A3. Завершение курса** — по достижении даты окончания напоминания
прекращаются, пациент получает уведомление.

### Исключения

**E1. Окно приёма истекло без подтверждения** *(шаг 3)* — приём
фиксируется пропущенным, пациенту показывается справочная информация.
Система не советует принять двойную дозу или пропустить следующую — это
было бы указанием по лечению.

**E2. Приверженность упала ниже порога** *(шаг 5)* — врачу поднимается
сигнал. Единичный пропуск сигнал не вызывает.

**E3. Уведомления отключены на устройстве** — при входе в приложение
пациент видит предупреждение, что напоминания не доставляются.

**E4. Схема изменена в момент активного окна** — текущее окно
завершается по старой схеме, новая вступает в силу со следующего дня.

### Постусловия

Успех: приём или пропуск зафиксирован с фактическим временем,
приверженность пересчитана.

## UC-04 — Работа врача со списком пациентов

**Уровень:** цель пользователя · **Основной актор:** Лечащий врач

**Предусловия:** к врачу подключены пациенты.

**Триггер:** врач открывает кабинет.

### Основной сценарий

1. Система показывает список подключённых пациентов.
2. Пациенты с флагами выведены первыми, с указанием причины.
3. Врач открывает карточку пациента.
4. Врач видит динамику симптомов, приверженность и последние записи.
5. Врач переходит к записи, вызвавшей флаг.
6. Врач принимает решение и фиксирует его.

### Альтернативные потоки

**A1. Флагов нет** *(шаг 2)* — врач видит сводку по активности ведения
дневников: пациент, переставший заполнять дневник, — тоже сигнал.

**A2. Подготовка к приёму** — врач открывает сводку за период перед
визитом пациента.

**A3. Приглашение нового пациента** — врач формирует приглашение,
пациент по нему подключается.

### Исключения

**E1. Пациент отозвал доступ** *(шаг 1)* — он исчезает из списка,
открытые флаги закрываются. Данные принадлежат пациенту, и отзыв доступа
безусловен.

**E2. Врач пытается открыть неподключённого пациента** — доступ
отклоняется.

**E3. Пациент перестал вести дневник** — отображается отдельно: отсутствие
данных не равно отсутствию проблем, и врач должен видеть разницу.

### Постусловия

Успех: врач просмотрел приоритетные случаи, решения зафиксированы,
обработанные флаги сняты.

## UC-05 — Назначение и изменение схемы терапии

**Уровень:** цель пользователя · **Основной актор:** Лечащий врач

**Предусловия:** пациент подключён к врачу.

**Триггер:** назначение или коррекция терапии.

### Основной сценарий

1. Врач открывает карточку пациента.
2. Врач задаёт препарат, режим приёма, терапевтическое окно и срок курса.
3. Система строит календарь приёмов.
4. Пациент получает уведомление о новой схеме.
5. Напоминания начинают приходить по новому календарю.

### Альтернативные потоки

**A1. Замена схемы** *(шаг 3)* — календарь перестраивается со дня
вступления в силу; история приёмов по прошлой схеме сохраняется.

**A2. Приостановка курса** — напоминания приостанавливаются с фиксацией
причины, приверженность за этот период не считается пропусками.

### Исключения

**E1. Схема пересекается с действующей по тому же препарату** —
требуется явно завершить предыдущую; параллельные схемы по одному
препарату не допускаются.

**E2. Терапевтическое окно не задано** — применяется значение по
умолчанию для формы препарата, врач видит его явно и может изменить.

**E3. Дата окончания в прошлом** — отклоняется.

### Постусловия

Успех: календарь соответствует действующему назначению, история прошлой
схемы сохранена, пациент уведомлён.

## UC-06 — Ведение справочника и шаблонов

**Уровень:** подфункция · **Основной актор:** Медицинский редактор

**Предусловия:** редактор авторизован, изменения проходят согласование.

**Триггер:** необходимость исправить формулировку, добавить статью или
профиль нозологии.

### Основной сценарий

1. Редактор открывает статью или шаблон.
2. Редактор вносит правку.
3. Изменение проходит согласование.
4. Система публикует новую версию, сохраняя предыдущую.
5. Пациенты видят обновление без переустановки приложения.

### Альтернативные потоки

**A1. Новый профиль нозологии** *(шаг 1)* — редактор задаёт набор
симптомов, шкалы и пороги; профиль становится доступен для назначения.

**A2. Расширение шаблона по обратной связи** — симптомы, которые пациенты
регулярно вводят вручную, попадают в отчёт как кандидаты на добавление.

### Исключения

**E1. Формулировка выходит за информационно-просветительский формат**
*(шаг 3)* — согласование не проходит. Именно формулировки определяют
регуляторный статус продукта, поэтому проверка обязательна, а не
рекомендательна.

**E2. Изменение порогов затрагивает активных пациентов** — новые пороги
применяются к новым записям; ранее поднятые флаги не пересматриваются
задним числом.

**E3. Откат версии** — публикуется предыдущая версия как новая; история
не переписывается, чтобы можно было восстановить, что читал пациент в
конкретный день.

### Постусловия

Успех: контент обновлён без релиза приложения, предыдущая версия
сохранена, соответствие формата подтверждено согласованием.
